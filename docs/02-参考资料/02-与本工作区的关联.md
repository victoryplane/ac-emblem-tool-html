## 二、★ 对既有笔记的两处订正 / 细化

### ① 「首块 sum 初值 `0x98`」—— 已独立验证，且知道它叫什么

`ACSL_CN\docs\01-侦察\92-外部情报调研.md` §4.5 记的「AC3 首块 sum 初值 `0x98`」**完全正确**，
而且本目录搞清了它的性质：它不是"初始累加值"，而是上游注释里说的
**"magic number"种子**，**只有第 0 段有**，其余 16 段累加器都从 0 开始；
LR 用的是 `0xB8`。完整公式：

```
每段 checksum = ( -( 段内数据之和 + 段内数据字节数 + 种子 ) ) & 0xFF
                种子 = 0x98（非 LR）/ 0xB8（LR），仅第 0 段
```

另：既有笔记写的「每 `0x400` 一个校验字节」在**物理**层面是对的，
但要知道每个物理块里是 **`0x3FF` 数据 + 1 校验**，
所以逻辑下标转物理偏移要走 `物理 = 起点 + 逻辑 + 逻辑 / 0x3FF` ——
**照 `0x400` 整块算会每 1023 字节错一格**。

### ② 「`BASLUS-20435S00`」vs「`BASLUS-20435E00`」—— **已定案** ✅

* `ACSL_CN\docs\01-侦察\92-外部情报调研.md` §4.5 记的存档名里有 **`S`** 开头的
  （AC3 `BASLUS-20435S00`、SL `BASLUS-20644E02/S00/S03`）；
* 上游 README 里**徽章存档**一律是 **`E##`**。

**现在有独立证据把两者区分开了**：公开存档库 `bucanero/apollo-saves` 的
Silent Line 页（[`PS2/SLUS20644/README.md`](https://github.com/bucanero/apollo-saves/blob/master/PS2/SLUS20644/README.md)）明确标注：

```
BASLUS-20644E02 : AC3SL Emblem No.3   ← 徽章存档
BASLUS-20644S00 : AC3SL No.1 SORTIE:029   ← 出击/剧情存档
BASLUS-20644S03 : AC3SL No.4 SORTIE:055
```

AC3 那页则只有 `S00`（出击存档）。
⇒ **`E##` = 徽章槽，`S##` = 出击/剧情存档**，两者同属一个游戏码。
`ACSL_CN\docs\01-侦察\92-外部情报调研.md` 记的 `S00` **没错，但那是出击存档，不是徽章存档** ——
所以当时那句"结构对 AC3 `0x4440` 吻合"说的其实是 `E##` 那一类文件名。

★ 附带产出：本目录**下载并验证了那个真实的 `BASLUS-20644E02`** ——
它是一个 `.PSV` 容器，徽章块在 `0x154`，**18/18 段校验全部通过**，
提取出来是一朵玩家自绘的红玫瑰。
详见 `../01-项目理解/04-记忆卡与存档处理.md` §三
与 `../../_selftest/02-真实存档验证.md`。

## 三、★ 一个必须分清的概念：**存档徽章 ≠ 碟内徽章贴图**

本工作区的笔记里大量出现 "emblem"，但**指的是完全不同的两样东西**：

| | 存档徽章（本工具管的） | 碟内徽章资源（汉化项目在处理的） |
|---|---|---|
| 是什么 | 玩家自己画的图案，存在记忆卡 | 游戏自带的徽章素材/编辑器 UI |
| 在哪 | `BASLUS-xxxxxE##` / `BASLUS-21338EMB/dataX` | ISO 里 `menu/emblem/**`、`menu/mrb/EmblemEdit.mrb` 等 |
| 格式 | 128×128 8bpp 索引色 + 调色板 + 每 0x3FF 一校验 | TM2 贴图 / MRB 容器条目 |
| 有文本吗 | **没有**（纯像素） | **有**（徽章编辑器 UI 标签、`emb_c###.tm2` 里的贴图碎片） |
| 本工具能碰吗 | ✅ 就是干这个的 | ❌ **完全不能** |

举例说明这个区分为什么重要：

* `ACFF_CN` 的批次 073/074/076/077 里，`menu/emblem/roadtolegend/emb_c###.tm2`
  被标为"**贴图/数据碎片（随机汉字串）**"、"留空或原样保留都是正确的"
  —— 那是**碟内** TM2 贴图被误当文本提取的结果，**与存档徽章毫无关系**。
* `ACNX_CN` 的术语表里有一批 `エンブレム` → 「徽章」的 UI 标签
  （`EmblemSelect.mrb`、`EmblemEdit.mrb`）—— 那是**碟内 UI 文本**，同样是另一回事。
* `ACSL_CN` §4.5 讨论的 `menu/emblem/font/*`（徽章编辑器小字库）也是碟内资源。

⇒ **本工具不会、也不能帮上这些汉化任务**。如果有人看到 "emblem" 就想到这个工具，
那是把两件事混了。

## 四、那它对汉化的**实际**用处是什么

诚实地说：**没有直接用处**（徽章里没有游戏文本）。但有三条间接价值：

1. **格式情报可迁移**。这套"每 `0x3FF` 数据插 1 个校验字节 + `-(sum+len+seed)`"
   的布局、以及"以 12 字节 u32 长度头当锚点在容器里定位子结构"的做法，
   很可能是 FromSoftware PS2 世代**存档侧的通用手法**。
   本工作区将来若需要碰存档数据（比如验证某个改动会不会破坏存档），
   这份格式文档是现成的参照。
2. **`dev` 分支的 PS1 知识是孤本**。`ExtractImageAC1` / `ApplyChecksumAC1` /
   `ListPS1MCBlocks` 那套（记忆卡块号定位、PS1 侧块校验 `-(sum + 0x38E2)`、
   Master of Arena 校验偏移不同）**在本仓库之外没有任何公开资料**，而且**从未发行**。
   它留在源码里，本目录已把它 clone 下来并写进 `../01-项目理解/05-源码导读.md` §五。
   本工作区有 `ACSL_CN` 在做的 PS1 世代相关工作可以参照。
3. **省下一件事**：以后不必再花时间搜"PS2 AC 徽章存档格式"——
   答案在本目录，且已与官方二进制交叉验证过。

### 5.3 ★ 一处需要订正的既有结论

`AC3_CN\docs\01-侦察\05-存档格式与跨区转换.md` 第 55 行写着：

> 「**没有**公开资料里的徽章魔数（`20 44 00 00 20 44 00 00 00 40 00 00`）出现 0 次
> ⇒ 那份公开结构（`mparley/ac-emblem-tool`）**对不上本作存档**，不能用。」

**这条结论下错了对象。** 该报告查的是 `S00` **出击存档**的数据文件
（41,600 B，`u32@0x00 = 41,552`）—— 而徽章在 **`E##`** 里，是完全另一个文件。
出击存档里当然不会有徽章头，这不能作为"公开结构对不上本作"的证据。

本目录的反证（都是实测）：

| 证据 | 内容 |
|---|---|
| ① **真实 SL 徽章存档** | `BASLUS-20644E02`（Silent Line = AC3 系）→ **12 字节头逐字节对上**、18 段校验 18/18、与官方 exe 逐像素一致（§二 上面已述） |
| ② **AC3 ELF 自己说的** | `AC3_CN\docs\01-侦察\08-存档校验逻辑(ELF).md` §2.1：`.sdata` 里有 `/BISLPS-25112E*`（**E = 徽章**）族，与 `AC3E.ICO`；并给出 E 族的读写长度 **`0x4420` = 17,440** —— **正好等于 `acet` 的 `kLRSaveSize`、也正好等于本目录从你卡上取到的 `data0` 的字节数** |
| ③ **你卡上的真实 LR 徽章** | `BISLPS-25462EMB/data0` = **17,440 字节**，用本实现 → 判定 LR、**校验 18/18**、与官方 exe **逐像素一致**（§5.4） |

⇒ 正确说法是：**公开结构对不上的是 `S##` 出击存档（本来就不该对上），对 `E##` 徽章存档是对得上的。**

### 5.4 ★ 从你卡上取到的真实 LR 徽章（2026-10-04，只读）

用 AC3_CN 现成的 `61_mc_survey.py` 的 `Card` 类**只读**读取（未向记忆卡写入任何字节）：

```
记忆卡 : C:\Users\M\Documents\PCSX2\memcards\Mcd001.ps2
目录项 #13  BISLPS-25462EMB        ← BISLPS-25462 = AC:LR 日版（SLPS-25462）
   ├ static.ico      28,110 B
   ├ data0           17,440 B     ← ★ 真实 LR 徽章，首 4 字节 00 44 00 00
   ├ icon.sys           964 B
   └ BISLPS-25462EMB     32 B
⇒ 已取出 → testdata/real/BISLPS-25462EMB_data0.raw
```

实测结果（**关闭了本目录此前最大的一个空白**）：

```
判定        : Last Raven 原始徽章存档 (0x4420)     ← 布局判定正确
校验字节    : 18/18 段全部通过                      ← LR 种子 0xB8 + 不分段乱序，实测成立
与官方 exe  : 逐像素 65,536 字节完全一致
提取结果    : 一个**完全不透明**的紫蓝色恶魔脸徽章（128×128 满幅）
```

★ 这份样本还纠正了一个本目录原先的说法（见 `../01-项目理解/02-存档格式规范.md` §五）：
**"透明 = 索引 0" 是错的**。真相是 **透明与否只看调色板项的 `alpha == 0`**：

```
LR  data0      palette[0] = 00 00 00 40   ← alpha=0x40 ≠ 0 ⇒ 索引 0 是个**不透明深色**
                                              ⇒ 全图 0 个透明像素
SL  E02        palette[0] = 00 00 00 00   ← alpha=0       ⇒ 索引 0 透明，10,922 px 透明
```
"索引 0 固定留给透明"只是**写入端**（`acet` 的 `palette_map` 初值）的约定，不是格式规则。
另外 LR 这份的 alpha 是 **`0x40`** 而不是 `0x80` ⇒ **alpha 的取值不止 0/0x80 两种**，
但提取时"非 0 即不透明"，所以不影响显示。

### 5.5 因此，正确的分工是

```
第 2/1 层（记忆卡文件系统、容器）  ← ★ 已有：AC3_CN\tools\30-存档\60_mc.py 等，直接复用
第 3 层（从存档/容器里切出徽章块）  ← 上游的"魔数搜索"可参考，但建议改用连续搜索 + 上面第 2 层精确取文件
第 4 层（徽章块 ⇄ 图像）           ← ★ 本目录：tools/acet_format.py（已与官方 exe + 两个真实存档验证）
```

★ **不要再重写一遍记忆卡层**（`AC3_CN` 那套踩过的坑已经写在它的 `AC3_CN\AGENTS.md` §9 里：
ECC 的 `(~i) & 0x7F`、dirent bit15、`icon.sys` 必须同步、读-改-写必须从副本句柄读…）。
徽章这一侧只需要接上"第 4 层"，再加上把 `E##`/`EMB/dataX` 从卡上取出来这一步。
