# 图片处理管线

> 这一页只讲一件事：**任意一张图，是怎么变成存档里那 0x4000 + 0x400 字节的**，以及反过来。
> 目标是把上游的规则讲到"可以照着重新实现"的程度。
>
> 标 ★ 的是**实测**（用官方 exe 在真实存档 / 合成存档上跑出来的），
> 其余为源码直读。所有结论都在 `tools/` 里有可执行的等价实现。

## 一、全景：两条入口，一个核心

```
                       ┌─────────────────────────────────────────┐
  CLI（acet-cli）      │  LodePNG 解码 → RGBA8                   │
  只吃 PNG  ──────────▶│  **不做任何缩放 / 减色 / 遮罩处理**      │
                       └────────────────┬────────────────────────┘
                                        │
                                        ▼
                       ┌─────────────────────────────────────────┐
  GUI（acet-gui）      │  wxImage 解码（PNG/BMP/GIF/JPEG/TIFF…）  │
  吃多种格式 ─────────▶│  ① alpha→mask  ② 缩放  ③ 减色          │
                       └────────────────┬────────────────────────┘
                                        │  128×128×4 的 RGBA 缓冲
                                        ▼
                       ┌─────────────────────────────────────────┐
                       │  InjectImage()   ← 格式核心，两个前端共用 │
                       │  ④ 建调色板（首次出现顺序）              │
                       │  ⑤ 写像素索引（非 LR 要乱序重排）        │
                       │  ⑥ 重算全部校验字节                      │
                       └─────────────────────────────────────────┘
```

★ **关键区别**：`InjectImage()` 之前的四道工序**全在 GUI 里**，CLI 一道都没有。
所以"CLI 必须自己先把图弄合规"，"GUI 能直接吃 JPG"。

★ 读上面那张图时请注意：**两行属于两条不同的入口** —— 「不做任何缩放/减色/遮罩」说的是 **CLI**，
「① alpha→mask ② 缩放 ③ 减色」说的是 **GUI**。别把 CLI 那条套到 GUI 上
（§六 的表格是 **GUI ↔ 本目录的 Python 实现** 的对照，两栏都会缩放和减色）。
本目录的 Python 实现（`tools/prepare_image.py`）走的是 **GUI 那条路**。

## 二、四道预处理工序（只有 GUI 有）

源码：`src/ac-emblem-tool/acet-gui/acet-gui.cpp:190-243`（`MainFrame::InjectHelper`）

```cpp
int colors = 256;
if (!image.HasMask()) {
    if (!image.HasAlpha()) { image.InitAlpha(); colors = 255; }
    image.ConvertAlphaToMask();                     // ① alpha → 1 bit mask
}
if (image.GetWidth() > 128 || image.GetHeight() > 128)
    image.Rescale(128, 128);                        // ② 缩放
if (image.CountColours(colors+1) > colors) {        // ③ 减色
    wxPalette *pal = NULL;
    if (wxQuantize::Quantize(image, quantized, &pal, colors, 0,
                             wxQUANTIZE_FILL_DESTINATION_IMAGE))
        image = quantized;
}
for (y…) for (x…) {                                  // ④ 逐像素取 RGBA
    if (image.IsTransparent(x,y)) push(0,0,0,0);
    else push(GetRed, GetGreen, GetBlue, 0xFF);
}
```

### ① alpha → 1 bit（阈值 128）

`wxImage::ConvertAlphaToMask()` 默认阈值 **128**：`alpha >= 128` 变不透明，
`< 128` 变全透明。之后所有判断都走 `IsTransparent()`。

⇒ **半透明从此不存在**。想要"柔和边缘"，只能在源图里手工做抖动（dither），
或者接受硬边。这是格式决定的（存档里 alpha 只有 `0x00` / `0x80` 两种值），不是工具偷懒。

### ② 缩放 —— ★ 上游这里有个坑

条件是 `宽 > 128 || 高 > 128`，也就是**只缩"大于 128"的图**。
一张 64×64 的图**不会被缩放**，但紧接着的循环照样按 `x,y ∈ [0,127]` 取值
⇒ **越界读**，行为未定义（可能断言、可能读到 0）。

⇒ **喂 GUI 的图请先自己补到 ≥128×128。**（这是限制问题 5。）

### ③ 减色

`wxQuantize::Quantize(..., colors, 0, wxQUANTIZE_FILL_DESTINATION_IMAGE)`，`colors` 取 256；
**只有原图没有 alpha 通道时**才降到 255（因为要空出一项给"透明"）。

⇒ GUI 会自动减色，所以它不怕照片；CLI 不减色，超限就出问题（见 §五）。

### ④ 输出成 RGBA 缓冲

透明像素输出 `(0,0,0,0)`，不透明输出 `(r,g,b,0xFF)`。
注意：**透明像素的 RGB 被丢弃**（写成 0），所以透明区域底下原来是什么颜色无关紧要。

## 三、核心：`InjectImage()` 怎么建调色板与索引

源码：`src/ac-emblem-tool/acet/acet.cpp:111-177`

```c
unordered_map<uint32_t,int> palette_map = { {PackColor(0,0,0,0), 0} };   // 透明项固定占 0

for (i = 0; i < 像素数; i++) {
    uint32_t c = 0;
    if (image[i*4+3] == 0xFF)                        // 只有"完全不透明"才保留颜色
        c = PackColor(r, g, b, 0x80);                // ★ alpha 存 0x80，不是 0xFF
    if (c 是首次出现) {
        if (palette_map.size() > 256) throw;         // ⚠ 差一，见 §五
        palette_map[c] = palette_map.size();         // 按"首次出现顺序"发号
        for (ch = 0..3)                              // 立刻写进调色板区
            save[OffsetIndex(image_offset + 0x4000 + idx*4 + ch)] = (c >> (24-ch*8)) & 0xFF;
    }
    int p = isLR ? palette_map[c] : UnscramblePalette(palette_map[c]);
    save[OffsetIndex(i + image_offset)] = p;         // 写像素索引
}
```

四条必须记住的规则：

| # | 规则 | 为什么 |
|---|---|---|
| 1 | **写入端**把透明项固定放索引 0（循环前就进 map） | 这是 `acet` 的**约定**，不是格式规则 —— 格式规则是"alpha==0 才透明"，见 §四 前的说明 |
| 2 | 调色板**按颜色首次出现的顺序**发号 —— 不是按亮度、不是按频率 | 决定索引到槽位的映射；顺序无所谓，但要自洽 |
| 3 | 不透明色的 **alpha 存 `0x80`** | ★ 真实 SL 存档实测：所有在用项都是 `xx xx xx 80`。⚠ 但**格式不要求恰好 `0x80`** —— 真实 LR 存档里 `palette[0]` 是 `00 00 00 40`。因为提取时"非 0 即不透明"，取值不影响显示 |
| 4 | 写进像素区的索引要过一次 `UnscramblePalette`（**仅非 LR**） | 见下 |

### 调色板乱序重排（仅非 LR）

```c
uint8_t UnscramblePalette(uint8_t index) {
    switch ((index % 32) / 8) {
        case 1: return index + 8;
        case 2: return index - 8;
        default: return index;
    }
}
```

以 **32 项为一组**，交换中间两组 8 项：

```
槽位:  [0..7][8..15][16..23][24..31]
索引:  [0..7][16..23][8..15][24..31]
```

★★ **这个置换是对合**（做两次等于没做）。所以上游"写入时重排一次、
提取时又重排一次"两次相抵、结果正确。**自己重写时两处都要有**，
只做一处会得到颜色全乱的徽章 —— 这是这段代码最容易看漏的地方。

★ 真实存档实测：索引 `9 → 槽位 17`、`10 → 槽位 18`，与上式完全吻合。

### 像素的物理位置不是线性的

```
物理偏移 = 徽章块起点 + 逻辑下标 + 逻辑下标 / 0x3FF
```
每 1023 个数据字节后面有 1 个校验字节，所以**每 1023 字节要空出一格**。
图像逻辑下标从 `0x24` 起（LR 从 `0x4` 起），调色板从 `0x24+0x4000` 起。

⇒ 写第 k 个像素是 `save[base + 0x24 + k + (0x24+k)/0x3FF]`，**不是** `base + 0x24 + k`。

## 四、反方向：`ExtractImage()`

```c
for (i = 0; i < 0x4000; i++) pixels[i] = save[OffsetIndex(image_offset + i)];
for (i = 0; i < 0x400; i++) {
    uint8_t c = save[OffsetIndex(image_offset + 0x4000 + i)];
    if (i % 4 == 3 && c != 0) c = 0xFF;              // ① alpha 只有"有/无"
    colors[i] = c;
}
image[i*4+c] = isLR ? colors[pixels[i]*4 + c]        // ② LR 直接用
                    : colors[UnscramblePalette(pixels[i])*4 + c];   // 非 LR 再重排一次
```

① ★★★ **透明看的是 `调色板索引 0`，不是 alpha 字节** —— 这一条是**实机定案**的。

上游的判据是"非 0 即不透明"（只看 alpha）：

```c
if (i % 4 == 3 && c != 0) c = 0xFF;
```

而**游戏看的是索引**：索引 0 起背景/透明的作用，**它的 RGB 与 alpha 都不当颜色画**。

依据（实机实测）：把 `data0` 的调色板 RGB 全部取反、alpha 原样保留
（`palette[0]`：`00 00 00 40` → **`FF FF FF 40`**）写进卡上的新槽 `data2`，进游戏看：

| 假设 | 预期 | 实测 |
|---|---|---|
| 按 alpha 混合 | 50% 白 ⇒ 成片中灰 | ❌ 找不到成片中灰 |
| 按 RGB 画 | 纯白 | ❌ 找不到成片纯白 |
| **索引 0 = 背景** | **黑** | ✅ **背景仍是黑的** |

三档提取对照（角像素 = 背景；**只有 `index0` 三个都对**）：

| 样本 | `palette[0]` | `--alpha acet` | **`--alpha index0`** | `--alpha gs` |
|---|---|---|---|---|
| `data0` 恶魔脸 | `00 00 00 40` | 不透明黑 | **透明** ✅ | 50% 黑 |
| `data1` 红树 | `00 00 00 00` | 透明 | 透明 | 透明 |
| `data2` 反色恶魔 | `FF FF FF 40` | 不透明**白** ❌ | **透明** ✅ | 50% **白** ❌ |

⇒ **想看"游戏里到底长什么样"，用 `--alpha index0`。**
（`acet` 档留给与官方 exe 的逐像素对齐；`gs` 档只是"把 alpha 字节当真"，实机证明不是游戏行为。）

★ 顺带：**写入端仍然只写 `0x00`/`0x80` 两种 alpha**（`if (alpha == 0xFF) → c = PackColor(r,g,b,0x80)`）。
因为游戏看索引，所以**照游戏的习惯写最省事**：背景放索引 0、其余色 `alpha = 0x80`。

② 非 LR 要**再过一次** `UnscramblePalette`（对合，与写入相抵）。

## 五、颜色数：边界与失败方式

| 不透明颜色数 | 调色板项数 | 结果 |
|---|---|---|
| 0 | 1（只有透明） | 全透明徽章，能写但没意义 |
| 1 – 255 | 2 – 256 | ✅ 完全正常 |
| **256** | **257** | ⚠ 上游判据是 `size() > 256`，第 257 项**会被放进来**；索引 256 写进 1 字节 ⇒ 截断成 **0** ⇒ 该颜色的像素变成**透明洞**，且**不报错** |
| 257+ | — | 同上，多出来的颜色依次串到索引 0 上 |

⇒ **安全上限就是 255 色 + 透明**。上游 README 明文写的就是 255。

★ **跨工具旁证**：zk306 的 AC:LR 转换器说明里写着
*"colors beyond the first 256 will be dropped. pixels using these colors will be rendered transparent."*
—— 另一个独立工具撞上了**同一个**失败方式，说明这是格式/惯例层面的边界，不是 acet 独有。

★ 本目录的处置：`acet_format.inject_image()` 默认 `strict=True`，遇到第 257 项**直接报错**；
`tools/acet_cli.py` 注入前会先量化统计并提示；
`tools/prepare_image.py` 保证输出 ≤255 色并**独立复核**。

## 六、上游 GUI 预处理 ↔ `tools/prepare_image.py` 对照

| 工序 | 上游 GUI | `prepare_image.py` | 差异理由 |
|---|---|---|---|
| 解码 | `wxImage`（多格式） | Pillow（多格式） | 等价 |
| alpha → 1 bit | `ConvertAlphaToMask()`，阈值 128 | `--alpha-threshold`，默认 128 | 等价 |
| 缩放 | **只缩 >128 的**（<128 会越界读） | **一律缩到 128×128** | 修掉上游的坑 |
| 缩放后 alpha | 不再二值化 | **再二值化一次** | 插值会造出新的半透明像素 |
| 减色 | `wxQuantize`（颜色数 `colors+1` 判据） | 中位切分，**只对不透明像素**，透明像素不占槽位 | 避免透明像素白占调色板项 |
| 复核 | 无 | **独立数一遍不透明色数并断言 ≤N** | 上游那个差一 bug 就是因为没有独立判据 |

★ **实测**（当时的输入样例是一张 300×300 的硬图，已随收尾清理删除；数字仍有效）：
一张 300×300、**49,444 色**、含 **27,919 个半透明像素**的图 ——

```
① alpha 二值化(阈值 128)：半透明像素 27919 个已归一
② 缩放 300x300 → 128x128 (LANCZOS)，alpha 重新二值化
③ 减色：11087 色 → 255 色（中位切分，仅对不透明像素）
④ 最终：15252 个不透明像素用 255 种颜色（调色板占 256 项）
→ 用**官方 acet.exe** 注入真实存档 → 校验 18/18 通过 → 读回**逐像素一致** ✅
```

## 七、全生态的"图片要求"对照表（互操作陷阱地图）

同一个徽章二进制，各家工具要求的输入格式**完全不一样** —— 这是这一整块最容易浪费时间的地方：

| 工具 | 覆盖 | 要求的输入 | 备注 |
|---|---|---|---|
| **acet CLI** | PS2 全系 | **PNG**，恰好 128×128，≤255 色，1 bit 透明 | 不缩放、不减色 |
| **acet GUI** | PS2 全系 | PNG/BMP/GIF/JPEG…，自动缩放减色 | <128×128 有越界 bug |
| Chase 的 AC3 工具（2013） | AC3 | **GIF 或 8-bit PNG**，128×128 | 输入是 **PSU** |
| zk306 的 AC:LR 转换器（2013） | ACLR | **24-bit BMP，且要预先水平翻转**，128×128，≤256 色，**左上角像素 = 透明色** | 输出 `data0..data7`；说明里点名"文件必须**恰好 17440 字节**" |
| MLR 1.05（kappa，VB6） | ACLR | **256 色 BMP**，128×128，BMP 文件**恰好 17,462 字节** | 17,462 = 54 头 + 1024 调色板 + 16,384 像素，正好是 8bpp BMP |
| PSX-Emblem（alerner） | PS1 AC1/PP/MoA | **64×64** BMP/PNG，**硬编码 16 色调色板** | 见 `04-记忆卡与存档处理.md` §八 |
| PSP-Emblem（alerner） | PSP AC3/SL/LR/FF | **128×128** BMP/PNG | PSP 保存数据格式，不是 PS2 |

★ **关于"水平翻转"**：zk306 要求输入 BMP **先水平翻转**，MLR 的 1.01 版也修过
"输出左右镜像"。本目录用官方 acet.exe 提取真实存档得到的是一朵**正立**的红玫瑰
（不是镜像），说明**读出方向是对的**；至于写回去后游戏里显示是否与编辑器一致，
`[未观测]`，值得实机确认一次（这是唯一需要你亲自跑 PCSX2 的点）。

## 八、症状 → 病因 对照表

| 你看到的现象 | 最可能的原因 |
|---|---|
| 徽章整体颜色错乱 / 像被洗过 | 非 LR 的 `UnscramblePalette` 只做了一次（写或读只做了一处） |
| 图上出现**透明洞**，位置对应某个颜色 | 颜色数到了 257，第 257 项索引被截断成 0 |
| 边缘锯齿消失、半透明区域整片变成硬边或消失 | alpha 被压成 1 bit（这是格式决定的）；或 GUI 阈值 128 切掉了浅色边 |
| 图整体偏移、色彩斑驳 | 忘了"每 0x3FF 字节空一格"的物理偏移规则 |
| 注入后存档校验不过 | 改了数据没重算校验字节（`apply_checksums`） |
| 一注入就报"颜色太多" | 用了 CLId 路径但没先减色 |
| GUI 里出现崩溃/断言，图很小 | <128×128 的越界读（上游限制问题 5） |
| 游戏里说存档损坏 | 见 `07-限制与已知问题.md` 问题 8 —— **末段（第 18 段）校验字节写早了 / 没按真实位置 `0x4435`（LR `0x4415`）写**，这是目前已知最常见的原因；另有外层容器校验、`E##`/`S##` 差异等可能 |

## 九、如果你自己做 GUI：这一段建议照抄

图像这块，建议按这个顺序做，并且**每一步都留一个独立判据**（上游就是缺判据才留下那个差一 bug）：

```
1. 解码任意格式            → RGBA 缓冲
2. alpha 二值化（阈值可给用户调，默认 128）
3. 缩放（一律缩到目标尺寸，不要只缩大图）
4. 再二值化一次 alpha      ← 缩放会造出新的半透明像素
5. 减色到 ≤255 色
6. ★ 独立复核：不透明像素的不同 RGB 数 ≤ 255 ？
       且 半透明像素数 == 0 ？
   两个都为真才允许写存档；否则报错，别静默继续
7. 预览时按"游戏会看到的样子"渲染（硬边、索引 0 透明），
   不要用带 alpha 渐变的预览骗自己
```

★ 第 6 步的两个断言，本目录已经写成可复用的函数：
`tools/prepare_image.py::count_opaque_colors()` 与 `--check-only`。
```
python tools\prepare_image.py 你的图.png --check-only
```
