## 🔴 1. `FindOffset()` 是**子序列**搜索，不是子串搜索 `[源码直读]`

`acet.cpp:30-55`：

```c
for (size_t i = 0, j = 0; i < save.size(); i++) {
    if (j == sizeof(kEmblemHeader)) { offset = i - j; found = true; break; }
    else if (save[i] == kEmblemHeader[j]) j++;
    else j = 0;
}
```

匹配上就 `j++`、失配就 `j = 0`，但**不要求这 12 个字节相邻**。文件里只要按顺序散落着
`0x20, 0x44, 0x00, 0x00, 0x20, 0x44, 0x00, 0x00, 0x00, 0x40, 0x00, 0x00`
（中间可以夹任意字节），就会定位到那个"起点"上。

**后果**：容器文件（`.psu`、记忆卡镜像）里如果碰巧有这种字节分布，
工具会**写出一个偏移错误的存档且不报任何错**。

**本目录的处置**：`tools/acet_format.py` 提供两个函数 ——
`find_offset()` 忠实复刻上游行为（保证字节级兼容），
`find_offset_contiguous()` 是正确的连续搜索。自检会比对两者，
在测试数据上一致，但**真实 `.psu` 上不保证一致**。

**建议**：往容器里写之前，先用 `python tools\acet_cli.py <文件> --info` 看它报的
"徽章块起点"合不合理；有疑问就用裸存档，别用容器。

## 🔴 2. 第 257 个颜色会被**静默截断**成索引 0（串色） `[源码直读]`

`acet.cpp:124-139`：

```c
if (palette_map.find(c) == palette_map.end()) {
    if (palette_map.size() > 256)                 // ⚠ 应该是 >= 256
        throw std::runtime_error("... more than 255 colors + alpha ...");
    palette_map[c] = palette_map.size();
```

调色板从 1 项（透明）起步，判据是 `> 256` 而不是 `>= 256`，所以**第 257 项会被放进来**，
它的索引是 **256**；而 256 写进 1 字节字段时会变成 **0**：

```c
save[OffsetIndex(i + image_offset, emblem_offset)] = p;   // p = 256 → 截断成 0
```

索引 0 是**透明色** ⇒ 该颜色在徽章上表现为**一片透明洞**，而且不报错。

**安全界限**：**≤ 255 色 + 透明**（即调色板总项数 ≤ 256）时完全正常。
恰好 256 色（255 色 + 1 透明）时，第 256 项索引 255 仍合法，也是安全的。
**只有 257 色才会中招** —— 但那正是"超过上限"的情形，本该被拦下。

**本目录的处置**：`inject_image()` 默认 `strict=True`，遇到第 257 项**直接报错**；
`tools/acet_cli.py` 在注入前先量化统计并给出提示。
想复刻上游的静默行为可以 `strict=False`。

★ **2026-10-04 追加（TS 移植时发现，已用 `offset_index` 独立复算确认）**：
**第 257 项（槽 256）的 4 字节物理位置正好压在"末段校验字节"上。**

```
palette[255] 逻辑 0x4420..0x4423 → 物理 0x4431 0x4432 0x4433 0x4434   （0x4434 = 末段 alpha）
palette[256] 逻辑 0x4424..0x4427 → 物理 0x4435 0x4436 0x4437 0x4438   （0x4435 = ★ 末段校验字节）
文件长度 0x4440（非 LR）
```

⇒ 上游把第 257 项写进调色板后，**末段校验又会把 `0x4435` 覆盖掉** —— 所以"越界写在校验位之前、
校验位最后写"这个顺序把上游的失败**完全掩盖**了：既没有坏校验，也让越界那 1 项的 R 通道被抹掉。
（本来那 1 项也永远不会被引用：图像索引是 1 字节，索引 256 写进去就是 0。）
⇒ 结论不变（判据仍是"**≤255 色 + 透明**"），但要知道：**要修这个 bug，必须同时处理这处物理重叠**。

## 🔴 3. 容器里的 **Last Raven** 存档会被当成非 LR 解析 `[源码直读]`

布局判定是 `bool isLR = save.size() == kLRSaveSize;` —— **只看文件大小**。
一个 `.psu` 包装过的 LR 徽章（大小 > 0x4420）会被判成 `isLR = false`，于是：

* 图像偏移取 `0x24` 而不是 `0x4` ⇒ 整体错位 0x20 字节；
* 多做一次 `UnscramblePalette` 乱序重排 ⇒ 颜色全乱。

**上游的规避方式**：LR 直接把裸 `dataX` 文件喂进去（README 明文要求）。
**本目录的处置**：`--info` 会明确打印判定结果；容器一律按非 LR 报告。

## 🟠 4. 错误路径会 `cin.get()` 等回车 —— **脚本调用会永久挂住** `[实测]`

`acet-cli/main.cpp:13-19`：

```c
void ExitMessage(std::string message) {
    std::cout << message << "\nExiting\n" << "Press enter key to continue...\n";
    std::cin.get();          // ← 卡在这里
```

## 🟠 6. GUI 与 CLI 对"半透明"的处理**不一致** `[源码直读]`

| | CLI (`main.cpp` → `InjectImage`) | GUI (`InjectHelper`) |
|---|---|---|
| 半透明像素 | `alpha != 0xFF` 一律**全透明** | 先 `ConvertAlphaToMask()`（默认阈值 128）⇒ alpha<128 全透明、≥128 不透明 |
| 缩放 | **不缩放**（非 128×128 会写坏） | 缩放到 128（但只缩大图，见问题 5） |
| 减色 | **不减色**（>255 色报错） | 超过阈值就用 `wxQuantize` 自动量化 |
| 备份 | `<存档>.backup`（单文件） | `acet-backup/<时间戳>/<文件名>` |

⇒ **同一张半透明 PNG，用 GUI 和用 CLI 注入会得到不同的徽章。**
两边都不算"错"，但要知道自己在用哪个。

## 🟡 7. 格式本身只支持 1 bit 透明度 `[源码直读]`

存档里 alpha 只有 `0x00` / `0x80` 两种取值，提取时归一成 `0x00` / `0xFF`。
⇒ **徽章不能有抗锯齿边缘、不能有半透明叠加**。
边角要平滑，只能在源图里手工做"抖动 + 全透明像素"。

## 🔴 8. ★ 末段（第 18 段）校验字节：上游**写早了一个字节** ⇒ 非 LR 写入被判 `破損ファイル` `[实测 + 实机]`

> **2026-10-04 更正**：这一条原先写的是"末段校验位与调色板 255 号色共用同一格字节"。
> 真相是：**`0x4434` / `0x4414` 根本不是校验位，而是 `palette[255].alpha`**；
> 真正的末段校验字节在 **`0x4435`（非 LR）/ `0x4415`（LR）**。

上游 `InjectImage()` 的末段循环：

```c
s = (s - (save[prev_check + dangling] + 0x01)) & 0xFF;          // prev_check = 0x43FF
save[prev_check + dangling] = (~(s + dangling) + 1) & 0xFF;     // 0x43FF + 0x35 = 0x4434 ← 早一格
```

* `dangling`（`0x35` = 53 / `0x15` = 21）的**真实语义是"末段数据字节数"**，数据从 `0x4400` 开始；
  上游把它当"从 `0x43FF` 起算的偏移"用 ⇒ 校验位落在 `0x4434`，比正确位置少 1 个字节。
* **它平时能用**：只要尾部是游戏写的 `X 01 00*9`，旧式与新式**恒等**（互为同一方程的两条推论）。
* **什么时候坏**：**从空白块造**存档（尾部全 0）⇒ 两式相差 `0xFF` ⇒ 游戏判 `破損ファイル`。
  这正是 `nlrtest` / `nlrtest2` / `sltest2` / `probe` / `fill` / `bisect` **全部失败**的原因。
* **来历**（上游自己的 git 历史，已复核）：加 LR 支持之前，上游写的是 `prev_check + 0x36`
  （= `0x4435`，**本来就是对的**）；`4b288b4`（2022-12-22）把它换成 `dangling`（`0x35` / `0x15`）——
  **把"偏移"当成了"长度"**，于是差一个字节。详见 `../../_selftest/04-末段校验差一字节.md` §四.5。
* **副作用**：上游原地注入时会把 `palette[255].alpha`（`0x4434` / `0x4414`）写成校验值。
  格式上限 255 色、255 号色不会被引用，所以画面上看不出问题；但逐字节比对会发现这一格不是 `0x80`。
  本实现的写法**不覆盖**那一格（固定写 `0x80`）。

**本目录的处置（已修正）**：

* `apply_checksums()` 按**真实位置**写：先把 `palette[255].alpha` 写成 `0x80`、其后 10 字节写成 `01 00*9`，再逐段算校验；
* `verify_checksums()` 验真实位置；`verify_checksums_upstream()` 保留上游写法做对照；
* 自检新增回归断言：**"从尾部全零的块造 ⇒ 真实写法下末段必须不通过"**；
* 新写入器作用在 10 份真实存档上**逐字节复原**原文件；`tools/selftest.py` 对官方 exe 仍 25/25。

★ **状态：已定位、已修、✅ 实机已确认（2026-10-04）**。
验证卡 `out/evidence/Mcd001_final.ps2`（脚本 `_selftest/write_final_test.py`）的 **7 格
（NX `E00..E04` + SL `E00/E01`）全部正常读取，无一格 `破損ファイル`** ⇒ **非 LR 写入打通**，
且 NX 与 SL 两个作品都通过（修正是格式级的，不是某作品的怪癖）。
完整推导与数值证据 → `../../_selftest/04-末段校验差一字节.md`；格式细节 → `02-存档格式规范.md` §四。

## 🟡 9. 注入不清理调色板的**旧内容** `[源码直读]`

`InjectImage()` 只为"本次图像里出现过的颜色"写调色板项，**剩余 200 多项保持原样**
（可能是上一张徽章的残留颜色）。

* 因为像素索引也只用到 `0..N-1`，残留项不会被引用 ⇒ **正常情况下无害**。
* 但如果你想把改过的存档拿去做**逐字节比较 / 指纹**，会发现"没用到的调色板区域"
  仍然保留着旧数据，不是零 —— 别把它误当成"写坏了"。

★ **2026-10-04 追加**：本目录一度把"**未用调色板项为 0**"当成非 LR 写入被拒的**原因**
（`09-真实样本的调色板与索引结构.md` §五 第 7 次实验的假设）。该假设**已被证伪**：实验卡 `Mcd001_fill.ps2`（过程卡，已清理）
两格都 `破損ファイル` —— 而且那轮实验用的还是**旧写入器**（末段校验差一字节，见问题 8），
**没有任何判别力**。真实原因是问题 8。
⇒ 新入口 `encode_emblem()` 默认会把未用项填成 `00 00 00 80`（对齐游戏产物，槽 0 不动）。
★ **2026-10-04 实机定案："填"不是硬性要求** —— 判别格 `Mcd001_final.ps2` 的 NX `E03`
（**不填**未用项、末段校验字节因此是 `0x4B` 而非 `0xCB`）**同样正常读取**。
⇒ 填它只是"让输出与游戏自己产物同形"的保真做法；`acet_cli.py --no-fill-unused` 可关掉。

## 🟡 10. 工具不认识**外层容器自己的**校验/签名 `[推断]`

`.psu` / `.max` / `.xpo` / 记忆卡镜像这些包装格式，本身往往带长度、校验和、目录项。
本工具把整个文件读进来、只改内部徽章块、再原样写回（**容器外壳不会被拆掉**），
但**不会更新外壳自己的校验**。

⇒ 改完的 `.psu` 能否被存档工具/实机接受，**取决于那个包装格式自己有没有校验**。

**建议**：实机使用优先走 **PCSX2 的"Convert 成文件夹" → 改裸文件 → Convert 回去**这条路，
绕开所有外壳校验问题。

## 🟡 11. `FindPaletteOffset()`（拖放识别）基本认不出存档 `[源码直读]`

`acet.cpp:57-103`。判据是"某位置起 4 字节全 0、第 8 字节 = `0x80`、第 12 字节 = `0x80`"，
**与 12 字节魔数对不上**；而且：

```c
if (curr+i % 0x400 == 0x3FF) off = 1;    // 运算符优先级！实际是 curr + i == 0x3FF
for (int i = 0, off = 0; ...)            // off 每次循环都被重置为 0
```

⇒ `off` 几乎恒为 0，那半句只在文件最开头附近有意义。

**影响面**：只影响 GUI 的"拖一个文件进来，判断它是存档还是图"。
CLI 不依赖它（CLI 只用 PNG 签名区分参数）。

## 🟠 16. PS1：颜色数上限实际是 **15 色**，不是 16 `[源码直读]`

`dev` 分支 `InjectImageAC1()`：

```c
if (palette_map.size() > 16)          // ⚠ 应该是 >= 16
    throw std::runtime_error("... more than 255 colors + alpha ...");
...
emblemBytes[i/2] = (emblemColors[i+1] << 4) | (emblemColors[i] & 0b1111);
```

与 PS2 侧**一模一样的差一 bug**：第 17 项（索引 16）会被放进来，

**PS1 安全上限 = 15 色 + 透明**（错误信息里那句"255 colors"是从 PS2 侧复制粘贴来的，不相干）。

## 🟠 17. PS1：`.mcs`（`SC` 头）那条路疑似少算 0x200，且实际上走不通 `[源码直读]`

```c
if (header[0] == 'S') block = 0;      // 单个存档导出 .mcs
...
const size_t off = (0x2000 * block) + (0x820 * emblemSlot);   // block = 0
infile.seekg(off); infile.seekg(checksumOff /* 0x200 */, cur);
```

`.mcs` 文件本身还有 **0x200 字节的文件头**，而 `block = 0` 让它从文件偏移 0 起算
⇒ `0x200 + 0x820*slot` 落在**存档头**上，不是校验位/调色板。

更关键的是：`ListPS1MCBlocks()` **硬要求前两字节是 `MC`**，
CLI 的 `-ps1` 与 GUI 的 `PS1Dialog` 都调它 ⇒ 喂 `.mcs` 会直接抛
`"calling on non MC file"`。⇒ **PS1 路径实际上只支持整张 128 KB 记忆卡镜像。**

## 🔴 20. ★ 透明度：上游按 **alpha** 判，游戏按 **索引 0** 判 —— **两套规则不一致** `[实测真实存档 + 实机]`

**这一条改过两次，最后一次是拿实机画面定的**（过程见 `02-存档格式规范.md` §五）。

### 上游怎么写

```c
uint32_t c = 0;
if (image[i*4+3] == 0xFF) c = PackColor(r,g,b,0x80);   // 注入：只看 alpha
...
if (i % 4 == 3 && c != 0) c = 0xFF;                    // 提取：只看 alpha
```

### 游戏怎么看

★ 实机实测（把 `data0` 调色板 RGB 全取反 → `palette[0]` 变 `FF FF FF 40` → 写进新槽 `data2`）：

```
如果游戏按 alpha 判 → 背景该是「50% 白」→ 成片中灰      实测：找不到成片中灰 ❌
如果游戏按 RGB 画   → 背景该是「纯白」                 实测：找不到成片纯白 ❌
如果游戏按「索引 0 = 背景」→ 背景该是黑                 实测：**背景仍是黑的** ✅
```

⇒ **游戏不把索引 0 的 RGB/alpha 当颜色画**；索引 0 起的是背景/透明的作用。

### 三档提取，哪一档对得上眼睛

| `--alpha` | 规则 | data0 角像素 | 与实机 |
|---|---|---|---|
| `acet`（默认） | 非零 alpha → `0xFF` | 不透明黑 | 黑 ✅（**碰巧对**，因为原底色本来就是黑） |
| **`index0`** | **索引 0 透明、其余不透明** | **透明** | ✅ **正解** |
| `gs` | GS `0..0x80` 映射 | 50% 黑 | 黑 ✅（也是碰巧） |

★ 用 `data2`（`palette[0] = FF FF FF 40`）才分得开：`acet` 给**纯白**、`gs` 给**半透明白**，
**两个都与实机不符**；只有 `index0` 对。

### 后果：往返会改变"游戏看到的东西"

`data0` 往返一次：背景从「索引 0」挪到「索引 1 + 不透明黑 `00 00 00 80`」
（索引 0 用量 3,976 px → 6 px）。
* 显示上**看不出差别**（两种情况游戏里都是黑底）；
* 但**字节变了、语义变了** —— 逐字节比对会报差异，指纹类判据会失效。

⇒ **要"游戏里正确"，最省事的做法是照游戏的习惯写：背景放索引 0、其余色 `alpha = 0x80`。**
⇒ 想看真实外观，用 `python tools\acet_cli.py <存档> --alpha index0`。

## 🔴 21. ★ **恰好 256 色的徽章，往返就会被截断**（问题 2 的真实案例） `[实测真实存档]`

问题 2 说的差一 bug，在**真实数据上真的会触发**：

```
data0（恶魔脸）：acet 模式提取后，不透明像素的不同 RGB 数 = 256
                 ⇒ 注入需要调色板项 = 256 + 1（透明项）= 257
                 ⇒ 上游判据 `size() > 256` 放行 ⇒ 第 257 项索引 256 被截断成 0
实测：官方 exe 走一遍"提取→原样注入"，有 5 个像素颜色被改坏
```

| 样本 | 不透明色数 | 注入需要的调色板项 | 往返结果 |
|---|---|---|---|
| `data1`（红树） | 127 | 128 | ✅ **0 个像素变化** |
| `data0`（恶魔脸） | **256** | **257** | ❌ 5 px 被截断成索引 0 |

⇒ **"256 色"是一个危险档位**：正好卡在上游那个差一的边界上。
★ 通用教训：**"能提取"不等于"能原样写回"** —— 对同一份存档做"提取→注入"往返，
并与原文件比对，是发现这类问题最直接的办法（本目录的 `selftest.py` 就是这么设计的）。

## 🔴 22. ★ LR 的 4 字节块头 `00 44 00 00`：**写成 0 会让游戏直接卡死** `[实机]`

LR 存档（`0x4420`）没有非 LR 那 36 字节头，但**头 4 字节不是随便的**：

```
LR 头 4 字节 = 00 44 00 00   （u32LE = 0x4400 = 索引 0x4000 + 调色板 0x400 = 逻辑载荷长度）
```

⚠ **写成 `00 00 00 00` ⇒ 游戏不是报 `破損ファイル`，而是直接卡死** `[推断]`。
依据：`Mcd001_final2.ps2`（把"从零造的 LR 块"写进 `data2`）实测卡死，而该块与本目录其它
LR 块的**结构性差异**就是这 4 字节。
（⚠ 那次卡死**没有做隔离实验**，同时还有别的变量，所以这条因果只算 `[推断]`；
但"**块头必须与真实存档逐字节一致**"这条规则**是硬的**，见下面的判据。）

★ **2026-10-04 实机确认**：把块头按真实值（`00 44 00 00`）写之后，
`Mcd001_LRtest2.ps2` 里**从零造的两枚 LR 徽章（MIRAGE / CREST）在游戏里正常显示** ——
**LR 从零造写入通过**（此前 LR 只验证过"在真实块上原地改"）。

★ **本目录自己犯过这个错**：`make_blank_save()` 里的守卫写成 `if with_header and not is_lr:`，
**LR 分支根本不写头**。之所以长期没暴露，是因为 LR 此前只测过"在真实块上原地注入"
（头被原样保留），而"逐字节复原真实存档"那条判据只走 `apply_checksums`、
**根本不经过 `make_blank_save`**。

* 已修：新增 `LR_EMBLEM_HEADER` / `lr_header_from_save()`；`make_blank_save()` 两种布局都写块头。
* 已补回归断言（`../../_selftest/validate_writer.py` §四）：
  **"从零造"的块头必须与真实存档逐字节一致**（非 LR 比 `0x00..0x23`，LR 比头 4 字节）。
* 格式细节 → `02-存档格式规范.md` §二；经过 → `../../_selftest/04-末段校验差一字节.md` §十一。

★ **通用教训（比这一条更重要）**：只验证"读改写路径"是不够的。
**"从零创建"是另一条代码路径，必须单独拿真实存档做一次逐字节比对** ——
否则会出现"全部测试通过、但游戏卡死"。

## 🔴 23. ★★ **PCSX2 的"每游戏记忆卡覆盖"会盖掉对话框里的设置** —— 实测踩了一整轮的坑 `[实测 · 2026-10-04]`

**症状**：对话框里明明写着 `Slot 2 = Mcd001_TEST.ps2`，进 LR 后那个 slot 上显示的却是**另一张卡**
（源卡 `Mcd001_embdata2.ps2`）的内容；换卡、冷启动、退到主界面再进，**全都不变**。

**真因**：PCSX2 v2.x 的记忆卡设置分两层，**每游戏层赢**：

```
inis\PCSX2.ini                       ← 「设置 → 记忆卡插槽」对话框写的就是它（全局）
gamesettings\<序列号>_<CRC>.ini       ← Game Properties（每游戏设置）写的是它，**它覆盖全局**
```

本机实例：

```
C:\Users\M\Documents\PCSX2\gamesettings\SLPS-25462_FEBEC38B.ini
    [MemoryCards]
    Slot2_Filename = Mcd001_embdata2.ps2          ← 只对 LR(日版 SLPS-25462 / CRC FEBEC38B) 生效
```

⇒ 同一时刻：对话框显示 `Slot 2 = Mcd001_TEST.ps2`，而 `logs\emulog.txt` 里是
`McdSlot 1 [File]: Mcd001_embdata2.ps2`（`McdSlot 0` = 界面上的 Slot 1）。
**LR 读的从来不是对话框里那张卡。**

**这一行是怎么来的：时间线（2026-10-04，全部来自文件时间戳 + emulog）**

| 时刻 | 事件 | 证据 |
|---|---|---|
| 15:53:52 | 用户做出 `Mcd001_embdata2.ps2`（所谓的"data2 卡"） | 文件创建时间 |
| 16:08:40.05 | PCSX2 **v2.9.54**（nightly）启动 | 进程 StartTime |
| 16:08:46（开机 +6.1 s） | LR 首次读设置：此时该每游戏文件**还不存在** ⇒ 只插入 Slot 1 的 `Mcd001.ps2`，Slot 2 空 | `Loading game settings from …` / 只有一条 `McdSlot 0` |
| 16:08:58.95（+18.95 s） | 运行中改了这个游戏的记忆卡设置 | `Updating memory card configuration` → `Ejecting memory card 1 (port 1 slot 0) due to source change` → `McdSlot 1 [File]: Mcd001_embdata2.ps2` |
| 16:08:59.34 | PCSX2 把它存成 **LR 专属**配置：`gamesettings\SLPS-25462_FEBEC38B.ini` **在这一刻被创建**（创建时间 = 最后修改时间，此后 4.5 h 未再变动） | 文件时间戳 |
| 20:24:42 | 用户在**全局**对话框把 Slot 2 改成 `Mcd001_TEST.ps2`（写 `inis\PCSX2.ini`）并重启 LR；**同一秒**日志仍是 `McdSlot 1 [File]: Mcd001_embdata2.ps2` | 即用户报的"冷启动也没变" |

★ 判据：该 ini 的 `[MemoryCards]` 里**只有 `Slot2_Filename` 一个键**（既没有 `Slot1_*`，也没有 `_Enable`）
⇒ 这是**针对这个游戏的一次显式指定**，不是"全局设置的快照"；PCSX2 里"游戏自己的设置"优先于全局。
★ 它只在"改这个游戏自己的设置"时才会被写；对照组：`SLPS-25338_26D1C561.ini`（NX）今天启动过很多次，
时间戳仍停在 10-01 ⇒ **单纯启动游戏不会写这个文件**。

**证据三件套**（都能用 `python tools\check_pcsx2_slots.py` 一次打印）：

| # | 证据 | 内容 |
|---|---|---|
| 1 | 配置文件 | 全部 `gamesettings\*.ini` 里**只有** `SLPS-25462_FEBEC38B.ini` 覆盖了记忆卡；写于模拟器启动后第 19 秒 |
| 2 | 模拟器日志 | LR **每一次**启动都是 `McdSlot 1 [File]: Mcd001_embdata2.ps2`；对照 SL 那次是 `McdSlot 1 [File]: Mcd001_TEST.ps2`（跟随全局） |
| 3 | 内容指纹 | 源卡 `BISLPS-25462EMB\data0/1/2` = 深蓝紫 / 黑红 / **反白**（`data0` 取反：`0F0E2A` ↔ `F0F1D5`）= **画面上那三格** |

参考（确认机制真实存在，且 UI 上不好改）：
[PCSX2#9032](https://github.com/PCSX2/pcsx2/issues/9032)（每游戏记忆卡要重新插拔才生效）、
[PCSX2#10723](https://github.com/PCSX2/pcsx2/issues/10723)（已与全局冲突的每游戏记忆卡在 UI 上**改不动/删不掉**）。

**规矩**：
* **每次进游戏验证前，先跑 `python tools\check_pcsx2_slots.py`** —— 它直接回答"这次实际会读哪张卡"。
* 要清掉覆盖：编辑该 `gamesettings\*.ini`，删掉 `[MemoryCards]` 里的 `SlotN_Filename` 行（先备份）；
  或在模拟器「Game Properties」里用 reset 取消。
* ⚠ 这条**与游戏逻辑无关、也与"模拟器缓存/即时存档"无关**：
  `SLPS-25462_FEBEC38B.ini` 写于 `2026-10-04 16:08:59`，PCSX2 进程从 `16:08:40` 起**一直没关过**
  ⇒ 那一行成了 LR 的"永久"插卡配置。
  经过 → `../../_selftest/04-末段校验差一字节.md` §十四.5。
