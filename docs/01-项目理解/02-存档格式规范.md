## 一、两条布局，一句话分清

| | 非 LR | Last Raven |
|---|---|---|
| 覆盖作品 | AC2 / AC2AA / AC3 / SL / NX / NB | ACLR |
| 文件大小 | **0x4440** = 17472 B | **0x4420** = 17440 B |
| 图像数据偏移 | **0x24** | **0x4** |
| 调色板乱序重排 | **有** | **无** |
| 首段校验种子 | **0x98** | **0xB8** |
| 末段校验偏移 | **0x4435**（上游错写成 `0x4434`） | **0x4415**（上游错写成 `0x4414`） |
| 存档文件名形态 | `BASLUS-<游戏码>E<槽号>`，一个文件一个徽章 | `BASLUS-21338EMB/data<0..7>`，一个目录 8 个徽章 |

判定方式**只看文件大小**（上游 `bool isLR = save.size() == kLRSaveSize;`）：

```
size == 0x4420  → Last Raven 布局
size == 0x4440  → 非 LR 布局
size >  0x4440  → 容器：先按魔数找徽章块，再按"非 LR"解析   ← 见 §六 陷阱③
其它            → 上游直接报错「文件太小」
```

### ★ 两条布局其实是同一种东西

```
非 LR 文件 (0x4440) = [20 字节存档头] + [LR 式徽章块 (0x4420)]
                       0x00..0x13        0x20..0x443F
```
对得上：`0x20 + 0x4420 = 0x4440` ✓，`0x20 + 0x4 = 0x24` ✓。

证据是存档头那三个 u32LE `0x4420 / 0x4420 / 0x4000` —— 前两个就是"徽章块长度"，
第三个是"图像数据长度"。`[推断]` 这是 FromSoftware 把徽章块当成一个 0x4420 字节的
子结构来存，非 LR 时代在外面多包了 20 字节。

⚠ 但**校验分段不是**块相对的：上游的累加循环对非 LR 跑满 0x4440 字节（整个文件）、
对 LR 跑满 0x4420 字节，所以**末段的数据字节数**不同：非 LR `0x35` = 53，LR `0x15` = 21。
别以为可以无脑套同一套分段。

★ 这两个数就是上游源码里那个 `dangling` 常数的值。它的**真实语义是"末段数据字节数"**
（数据从 `0x4400` 开始），上游却把它当"从上一个校验字节 `0x43FF` 起算的偏移"用 ⇒ 校验位差 1 字节。
见 §四。

| 区段 | 长度 | 内容 |
|---|---|---|
| `0x00..0x0B` | 12 | 三个 u32LE：`0x4420` / `0x4420` / `0x4000`（= 载荷长度、同值、图像字节数） |
| `0x0C..0x13` | 8 | **全 0**（所有样本一致） || **`0x14..0x1C`** | **9** | ★ **作品级常量** —— 见下 |
| `0x1D..0x23` | 7 | **全 0**（所有样本一致） |

#### 这 9 字节是"作品级常量"，与徽章内容无关

**证据**：SL **美版**的玫瑰（`BASLUS-20644E02`，别的玩家、完全不同的图）
与 SL **日版**的 MIRAGE（`BISLPS-25169E00`）**这 9 字节完全相同**：

| 作品 | 值（0x14..0x1C） |
|---|---|
| **Silent Line**（日版 `SLPS-25169` / 美版 `SLUS-20644` **同值**） | `00 a1 30 dd 85 ab 07 80 60` |
| **Nexus**（日版 `SLPS-25338`） | `80 b2 30 dd 85 ab 07 80 60` |
| Last Raven | **无此区**（0x04 起就是图像） |
| AC2 / AC2AA / AC3 / NB | `[未观测]` —— **必须从真实的 `E##` 里读，别猜** |

★ 有趣的是：SL 与 NX 的这 9 字节**后 7 字节相同**（`30 dd 85 ab 07 80 60`），
只有前面 2 字节不同（`00 a1` vs `80 b2`）。含义未知，但对工具来说不重要 ——
**照抄即可**。

#### 工具怎么处理

```python
tail = af.header_tail_from_save(同作品的任意一个真实 E## 存档)   # ★ 最稳
# 或查 af.KNOWN_HEADER_TAIL（目前只有 SL / NX）
blk = af.make_blank_save(is_lr=False, header_tail=tail)          # ← 必须传！
```

⚠ **`make_blank_save()` 不传 `header_tail` 就会把这 9 字节填 0。**
⇒ 造新的非 LR 徽章时**务必传**（`[待复测]`：这一段是否真的会被游戏校验，见上面的追加更正；
无论如何，照抄真实存档是零成本的）。
（LR 没有这个字段 —— 但**"LR 写入一次就成功、非 LR 却失败"的真正原因不是它**，
而是末段校验位差一个字节，见 §四 与 `../../_selftest/04-末段校验差一字节.md`。）

### ★★ 那 12 字节"魔数"其实是**长度字段**，不是魔数

把魔数按 u32LE 读出来：`20 44 00 00 20 44 00 00 00 40 00 00` ⇒ **`0x4420` `0x4420` `0x4000`**。
再对上真实数据和本工作区另一条独立线索，就成了一个**贯穿全格式的统一解释**：

| 布局 | 文件大小 | 头 4 字节（u32LE） | 差值 | 解释 |
|---|---|---|---|---|
| 非 LR | `0x4440` = 17,472 | `0x4420` = 17,440 | **32** | 后两个字段：`0x4420`（同值）、`0x4000`（图像字节数） |
| LR | `0x4420` = 17,440 | `0x4400` = 17,408 | **32** | 后 12 字节为 0 |

★ **两种布局的头 4 字节都等于「文件大小 − 32」** —— 与它同时代同引擎的 `S##` 出击存档
**完全同构**（`AC3_CN` 实测：`BASLUS-20435S00` 文件 41,600 B，头 `u32@0x00 = 41,552`，
**差 48**；SL 的 `S00` 文件 62,432 B、自述 62,352、**差 80**）。

⇒ 所以这是 FromSoftware PS2 存档的**通用做法**：**文件开头一个"载荷长度"字段，
游戏只读它声明的那么多**。这解释了：
* 为什么 `FindOffset()` 能拿它当"锚点"在容器里定位 —— **它本来就是个有意义的头**；
* 为什么 LR 的 `kLRSaveSize = 0x4420` 会**恰好等于**非 LR 头里那个长度值 ——
  因为非 LR 文件就是「`0x20` 字节头 ＋ `0x4420` 字节载荷」，而 LR 文件是**没有那层头的同一份载荷**；
* `0x24 = 0x20 + 0x4`、`0x4024 = 0x20 + 0x4004`：非 LR 的图像/调色板偏移正好是 LR 偏移加上那个头长。

★ 还有一条**独立旁证**：`AC3_CN` 从 AC3 的 ELF（`SLPS_251.12`）反解出
存档族的读写长度，其中 **E 族（`/BISLPS-25112E*`，E = 徽章）= `0x4420` = 17,440**
（见 `AC3_CN\docs\01-侦察\08-存档校验逻辑(ELF).md` §2.1）。
—— 这与上面"载荷 = `0x4420`"**完全吻合**，等于游戏自己承认了这个长度。

⚠ **仍未定案**：AC3 的 `E##` 文件到底是 `0x4440`（带 32 字节头）还是 `0x4420`（纯载荷）。
`[未观测]` —— 本目录还没有 AC3 的 `E##` 真实样本。
两种可能都能解释 ELF 那个 `0x4420`（"读整个文件"或"只读载荷部分"）。
**拿到一个真实 AC3 `E##` 就能一句话定案。**

### 逻辑下标 ↔ 物理偏移

```c
size_t OffsetIndex(size_t i, size_t emblem_offset) {
    return emblem_offset + i + (i) / 0x3FF;
}
```
即 **物理 = 徽章块起点 + 逻辑 + 逻辑 / 1023**。`[已交叉验证]`

举例（`emblem_offset = 0`）：逻辑 `0x000` → 物理 `0x000`；逻辑 `0x3FE` → 物理 `0x3FE`；
逻辑 `0x3FF` → 物理 `0x400`（**跳过了物理 0x3FF 那个校验字节**）。

所以：**图像第 k 个像素的物理位置 = `0x24 + k + k/0x3FF`**，不是简单的 `0x24 + k`。
写这个格式最容易踩的坑就是这个 —— 每 1023 字节要空出一格。

## 三、字节级布局（Last Raven）

```
偏移        长度        内容
--------------------------------------------------------------------------
0x0000      4           头（4 字节，含义未观测）                     [未观测]
0x0004      0x4000      图像索引数据 128×128，8bpp
0x4004      0x0400      调色板 256×4 = R,G,B,A
--------------------------------------------------------------------------
0x3FF, 0x7FF, ... , 0x43FF   17 个常规校验字节（与非 LR 同位置）
0x4400..0x4414               末段数据 = 21 字节（最后一格 = 调色板 255 号色的 alpha）
0x4415                       末段校验字节（= 0x4420 − 11）
0x4416..0x441F               固定尾巴 01 00*9（10 字节），不参与任何校验
```

LR **不做调色板乱序重排**，这是它与非 LR 在解码上唯一的算法差别。

## 四、校验算法

### 结论

```
每一段：  checksum = ( -( 段内数据字节之和 + 段内数据字节数 + 种子 ) ) & 0xFF
          种子 = 0x98（非 LR）/ 0xB8（LR）  —— **只有第 0 段有**，其余段种子 = 0
```
`( -x ) & 0xFF` 就是上游写的 `~(x) + 1`。`[已交叉验证]`

### 分段

18 段 = 17 个常规段 + 1 个末段：

| 段 | 起点 | 数据字节数 | 校验字节位置 | 种子 |
|---|---|---|---|---|
| seg00 | `0x0000` | `0x3FF` | `0x03FF` | **0x98 / 0xB8** |
| seg01 | `0x0400` | `0x3FF` | `0x07FF` | 0 |
| … | … | … | … | 0 |
| seg16 | `0x4000` | `0x3FF` | `0x43FF` | 0 |
| seg17（末段） | `0x4400` | **`0x35` = 53（非 LR）/ `0x15` = 21（LR）** | **`0x4435` / `0x4415`** | 0 |

### ★★★ 末段校验位在 `0x4435` / `0x4415` —— **不是**"徽章块最后一个字节"

> **2026-10-04 更正**：本节原先的结论是"校验位落在 `0x4434` / `0x4414`，
> 与调色板 255 号色共用同一格"。那是**错的**：
> 那一格是 **`palette[255].alpha`**，真正的末段校验字节**在它后面一格**。

上游 `acet` 把末段校验写在 `0x4434` / `0x4414`，**整整早了一个字节**。真实布局：

```
               末段数据（长度 = 上游那个 dangling 常数）      校验        不参与校验的 10 字节
非 LR 0x4440   [0x4400 .. 0x4434]   53 B                [@0x4435]   [0x4436..0x443F] = 01 00*9
LR   0x4420   [0x4400 .. 0x4414]   21 B                [@0x4415]   [0x4416..0x441F] = 01 00*9
               ↑ 上一个常规校验字节在 0x43FF，末段数据从它**下一个字节**开始
```

* **`0x4434` / `0x4414` = `palette[255].alpha`**：调色板的物理范围是 `0x4034..0x4434`
  （LR `0x4014..0x4414`），槽 255 的 alpha 正好落在末尾
  （非 LR：逻辑 `0x4423` → 物理 `0x4434`；LR：逻辑 `0x4403` → 物理 `0x4414`）。
  `[已实测真实存档]` 10 份真实样本这一格**全是 `0x80`**（游戏对每一项的 alpha 都写 `0x80`，槽 0 除外）。
* ⇒ 上游的写法**会把 `palette[255].alpha` 覆盖成校验值**，并把真正的校验格留在原地。
  因为格式上限是 255 色 + 透明、255 号色不会被引用，画面上看不出问题 —— 这也是它一直没被发现的原因之一。

### `dangling` 到底是什么：**末段数据字节数**

上游末段写法：
```c
sum -= (save[prev_check + dangling] + 0x01);              // prev_check = 0x43FF
save[prev_check + dangling] = ~(sum + dangling) + 1;      // 0x43FF + 0x35 = 0x4434 ← 早一格
```
`dangling` = `0x35` = **53**（LR `0x15` = **21**）**就是末段的数据字节数**，数据从 `0x4400` 开始；
上游把它当成"从上一个校验字节 `0x43FF` 起算的偏移"用 ⇒ 校验位落在 `0x4434`，比正确位置少 1。
（`0x35 = 0x34 + 1` 这种"刚好落在块尾"的巧合，是它长期没暴露的原因。）

### 为什么上游"一直能用"：两套写法在真实存档上**恒等**

设 `S = sum(0x4400..0x4433)`，尾部 11 字节 `T = b[0x4435..0x443F]`：

| 写法 | 公式 |
|---|---|
| 上游（旧） | `b[0x4434] = -(S + sum(T) + 52) & 0xFF` |
| 真实（新） | `b[0x4435] = -(S + b[0x4434] + 53) & 0xFF` |

尾部形如 `X 01 00*9` 时 `sum(T) = X + 1`，两式**互为同一方程的两条推论** ⇒ 恒等。

* **原地注入**（上游工具的用法）：尾部是游戏写的 `X 01 00*9` ⇒ 恒等成立 ⇒ 一直"能用"；
* **从空白块造**（造新存档的用法）：尾部全是 0 ⇒ 恒等式被破坏，两式相差 **`0xFF`** ⇒ 游戏判 `破損ファイル`。

★ **来历（上游自己的 git 历史，第三条独立证据，已本目录复核）**：加 LR 支持之前，上游写的是
`save[prev_check + 0x36]`（`0x43FF + 0x36 = 0x4435` ✅ 位置对；值 `~(sum + 0xFF) + 1 + 0xCA`，
其中 `0xCA = 255 − 53` ✅ 长度也对）。`4b288b4`（"Added AC: Last Raven support"，2022-12-22）
为了兼支持 LR，把 `0x36` 换成了 `dangling`（非 LR `0x35`、LR `0x15`）——
**这两个数其实是"数据长度"而不是"偏移"** ⇒ 校验位从 `0x4435` 退到了 `0x4434`。
（同一次提交还顺手把常规段的 `0xFF` 改成 `0x3FF`，但两者模 256 等价，
所以**那次改动真正改变行为的只有这一处差一字节**。）
详见 `../../_selftest/04-末段校验差一字节.md` §四.5。

★ 这就是"非 LR 写入被游戏拒绝"的**根因**（见 `07-限制与已知问题.md` 问题 8）。
★ **实机已确认**（2026-10-04）：修正后 `out/evidence/Mcd001_final.ps2` 的 7 格全部正常读取 ⇒ 非 LR 写入打通。
★ 也因此 `verify_checksums()`（真实位置）与 `verify_checksums_upstream()`（上游位置）
**在 10 份真实存档上双双通过** —— 两个都过并不说明两套写法等价，只说明恒等式在真实存档上成立。
本实现写出的文件**同时满足两式**，所以官方 `acet.exe` 依然能正确读回。
`[已交叉验证]` 完整推导、数值证据与被推翻的旧结论 → `../../_selftest/04-末段校验差一字节.md`。

## 五、颜色与透明度

### 调色板乱序重排（仅非 LR）

以 **32 项为一组**，交换中间两组 8 项：

```
[0..7][8..15][16..23][24..31]   →   [0..7][16..23][8..15][24..31]
```
即 `(index % 32) / 8 == 1` → `index + 8`；`== 2` → `index - 8`；否则不变。

★ 这个置换是**对合**（做两次等于没做）。所以上游"写的时候重排一次、读的时候又重排一次"
不会出错 —— 两次相抵。照抄实现时**两处都要有**，只做一处会得到乱色徽章。

### ★★★ 透明度：以 **调色板索引 0** 为准（实机定案，2026-10-04）

> **这一节前后改过两次，最后一次是拿实机画面定的。** 把过程记下来，因为它是个好教训：
>
> | # | 说法 | 依据 | 判定 |
> |---|---|---|---|
> | ① | "透明项固定占索引 0" | 上游**写入端**的写法（`palette_map` 初值） | 当时被当成"只是约定" |
> | ② | "透明 = 该调色板项的 **alpha 字节 == 0**" | 真实存档里 `data0` 的 `palette[0] = 00 00 00 40`（非 0） | 当时据此推翻了 ① |
> | ③ | **"游戏看的是索引 0"** | ★ **实机实测**（下面那段） | ★ **定案** |
>
> 教训：**"字节里存了什么"和"游戏拿它干什么"是两件事。**
> 只看存档字节会得出 ② 这种自洽但错一半的结论；**必须有一次实机观测**才能收敛。

#### 实机怎么测的

把 `data0` 的调色板 **RGB 全部取反、alpha 原样保留**（于是 `palette[0]` 从 `00 00 00 40`
变成 **`FF FF FF 40`**）写进卡上的新槽 `data2`，进游戏看那一格：

| 假设 | 预期画面 | 实测 |
|---|---|---|
| ② alpha 当真（`0x40` = 50%） | 背景 = 50% 白 ⇒ **成片中灰** | ❌ 全格**找不到**成片的中性灰（100–190 只有散点，各值 ≲10 px） |
| ②′ 忽略 alpha、按 RGB 画不透明 | 背景 = **纯白** | ❌ 全格**找不到**成片纯白（>250 的众数是 `(225,228,203)` 这种奶白，是恶魔身体的反色，不是背景） |
| ③ **索引 0 就是背景色/透明** | 背景 = **黑**（与原图一样） | ✅ **背景仍是黑的**，与原恶魔那格一致 |

⇒ **游戏不把索引 0 的 RGB / alpha 当颜色画**；索引 0 起的就是"背景/透明"的作用。

#### 所以提取要这样

| `--alpha` 档位 | 规则 | 什么时候用 |
|---|---|---|
| `acet`（默认） | 任何非零 alpha → `0xFF` | 与**官方 exe 逐像素对齐**、做交叉验证 |
| **`index0`** | ★ **索引 0 透明、其余不透明（忽略 alpha 字节）** | ★ **想知道"游戏里到底长什么样"就用这个** |
| `gs` | 按 GS `0..0x80` 线性映射（`0x40`→127） | ⚠ **分析用**；实机已证明它不是游戏行为 |

真实数据三档对照（角像素 = 背景）：

| 样本 | `palette[0]` | `acet` | **`index0`** | `gs` |
|---|---|---|---|---|
| `data0`（恶魔脸） | `00 00 00 40` | 不透明黑 (255) | **透明** ✅ 与实机一致 | 50% 黑 (127) |
| `data1`（红树） | `00 00 00 00` | 透明 | 透明 | 透明 |
| `data2`（反色恶魔，我写的） | **`FF FF FF 40`** | 不透明**白** ❌ | **透明** ✅ 与实机一致 | 50% 白 (127) ❌ |

★ **`data2` 那一行是关键**：`acet` 档给出纯白、`gs` 档给出半透明白，**两个都和实机不符**；
只有 `index0` 档与实机一致。

#### 还没搞清的

* **索引 0 到底是"透明（露出底下的黑色底板）"还是"被强制画成黑"** ——
  两种解释在实机上都表现为黑，对本目录的用途没有区别，所以没再往下追。
* **alpha 字节到底有什么用** —— 256 项里只有索引 0 不是 `0x80`（`data0` 是 `0x40`、`data1` 是 `0x00`），
  而它对显示**没有可观测影响**。可能是残留、可能是给别的路径用的，`[未观测]`。

#### 与写入端的关系

* **注入时**：`alpha != 0xFF` 的像素一律变成完全透明 —— **半透明会被整片抹掉**。
  这与"游戏只看索引 0"是**两套规则**：上游按 alpha 判、游戏按索引判。
  实测后果：`data0` 往返一次，背景从"索引 0"挪到了"索引 1 + 不透明黑"（见问题 20/21），
  因为 `acet` 把索引 0 的非零 alpha 当成了不透明色。
* ⇒ 想做出"游戏里正确"的徽章，**最简单的做法是照游戏的习惯写**：
  **背景放索引 0、其余颜色 `alpha = 0x80`**。

### 颜色数硬上限 255（+ 透明 1 项）

调色板按"颜色首次出现的顺序"分配索引。上游的越界检查是 `if (palette_map.size() > 256)`，
**差一**：第 257 项会被放进来，而索引 256 写进 1 字节字段时截断成 0 ⇒ **静默串色**。
本目录的 Python 实现把这一条改成**报错**（见 `07-限制与已知问题.md`）。

## 六、定位徽章块

### 非 LR 的 12 字节魔数

```
20 44 00 00 | 20 44 00 00 | 00 40 00 00
   0x4420        0x4420        0x4000        ← u32LE
```
`0x4420` = LR 徽章块长度（出现两次），`0x4000` = 图像数据长度。`[推断]` 见 §一。

### 上游的定位逻辑（要照做）

```
size == 0x4440  →  offset = 0            （不搜索）
size == 0x4420  →  offset = 0            （不搜索）
size >  0x4440  →  在文件里搜魔数，offset = 魔数起点
size <  0x4440 且 != 0x4420  →  报错
```

### ⚠ 陷阱①：上游的"搜索"是**子序列**匹配，不是子串匹配

上游 `FindOffset()` 逐字节推进，匹配上就 `j++`、失配就 `j = 0`，但**不要求这 12 个字节相邻**
（见 `07-限制与已知问题.md` 的问题 1）。文件里若散落着 `0x20/0x44/0x00/0x40`，
定位就可能落在错的地方 ⇒ **写出错误偏移的存档**。

本目录的 `acet_format.find_offset()` 忠实复刻该行为（保证字节级兼容），
同时另给 `find_offset_contiguous()` 作为"正确"版本。自检会比对两者。

### ⚠ 陷阱②：容器里的 LR 存档会被当成非 LR

`isLR` 只由**文件大小**决定，所以一个 ≥0x4440 的 `.psu`/记忆卡容器，即便里面装的是
LR 徽章，也会被按非 LR 解析（图像偏移 0x24 而不是 0x4、还多做一次乱序重排）⇒ 结果全错。
上游 README 因此明文要求：**LR 必须直接把裸 `dataX` 文件喂进去**。

### ⚠ 陷阱③：`FindPaletteOffset()` 认不出徽章存档

上游用它判断"拖进来的文件像不像存档"，判据是"某位置起 4 字节全 0、第 8 字节和第 12 字节是 0x80"，
**跟 12 字节魔数对不上**；而且原式 `curr+i % 0x400` 因运算符优先级实际等于 `curr + i == 0x3FF`，
几乎只在文件开头生效。⇒ 拖放识别**不可靠**，别把 GUI 的拖放结果当成"识别成功"的证据。

## 七、文件从哪来（实操）

PCSX2 用户最省事：

1. 游戏内存档 → 存一个"徽章存档"（不是普通存档）；
2. PCSX2 → 记忆卡菜单 → **Convert**（把记忆卡转成文件夹）；
3. 在生成的文件夹里找：
   * 非 LR：文件与目录同名，形如 `BASLUS-20435E00`
     （`BASLUS-20435` = 游戏码，`E00` = 第 1 个徽章存档，`E01` 第 2 个…）
   * LR：目录 `BASLUS-21338EMB`，里面是 `data0` … `data7`
4. 改完再 Convert 回去 / 直接拷回记忆卡目录。

实机用户需要先把记忆卡导到 PC（`mymc` 等）。

## 八、上游明确不支持的输入

* **只有裸徽章数据**才保证可用。`.psu` / `.max` / `.mcd` 等"包装过的存档"，
  只要包装没有改动裸数据，v1.0.0+ 声称可以（作者只试过 `.psu`、`.sps`/`.xpo`），
  但**没在实机上验证过**；v0.0 则明确只吃裸数据。`[源码直读]`
* 容器里的 **LR** 徽章（见 §六 陷阱②）。
* 图像必须是 **128×128、≤255 色**。CLI 不做任何缩放/减色；
  GUI 会缩放（但只对"大于 128"的图缩放，见 `07-限制与已知问题.md` 问题 5）。
