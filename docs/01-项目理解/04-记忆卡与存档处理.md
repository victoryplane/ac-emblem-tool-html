# 记忆卡与存档处理

> 这一页讲清楚三件事：
> **① 上游到底怎么"找"到徽章数据；② 它根本不处理哪些记忆卡层面的东西；
> ③ 你要在自己的 GUI 里做记忆卡支持的话，需要补齐什么。**
>
> ★ 本页有一条**真实存档的实测验证**（§三），那是全目录最硬的一块证据。

---

## 一、结论先行（一句话）

> **上游 `main` 分支完全不处理记忆卡。** 它只吃"**已经导出成单个文件的徽章存档**"，
> 对容器（`.psu` / `.max` / `.PSV` / 记忆卡镜像）只有一招：**在文件里搜 12 字节魔数**。
> 唯一的"真正读记忆卡"的代码在**未发行的 `dev` 分支**，而且**只有 PS1**、且未完成。

源码核对（`git grep` 全分支）：

```
main    分支：memory card / mcr / mcd / psu 相关标识符  →  **零命中**
dev     分支：ExtractImageAC1 / InjectImageAC1 / ApplyChecksumAC1 /
              ListPS1MCBlocks / isPS1Save            →  PS1 记忆卡支持（半成品）
```

## 二、PS2 侧的记忆卡层次，以及"上游站在哪一层"

```
真实记忆卡（8 MB，Sony 文件系统 + ECC）
   └─ 存档目录（一个游戏一个目录，如 BASLUS-20644E02）
        └─ 目录里的文件：图标、icon.sys、**徽章数据块（0x4420 / 0x4440）**
                                                      ▲
                                        ★ 上游只处理这一层
```

### 上游能吃的三种输入

| 输入 | 上游怎么处理 | 可靠性 |
|---|---|---|
| **裸徽章存档**（恰好 `0x4440`，非 LR） | `size == kSaveSize` ⇒ 偏移 0，直接干 | ✅ 最稳，README 推荐 |
| **裸 LR 存档**（恰好 `0x4420`） | `size == kLRSaveSize` ⇒ 偏移 0 | ✅ 但**必须是裸文件** |
| **容器**（`.psu` / `.max` / `.PSV` / 任何更大的东西） | `size > 0x4440` ⇒ **在全文件里搜 12 字节魔数**，偏移 = 魔数起点 | ⚠ 见 §四 |

### ★ 那个"通用容器处理"是什么

`FindOffset()`：在文件里按顺序匹配

```
20 44 00 00 20 44 00 00 00 40 00 00
```

匹配到就把**魔数起点**当作徽章块起点，之后所有读写（像素、调色板、校验）
全部按 `物理 = 起点 + 逻辑 + 逻辑/0x3FF` 走。

**好处**：**完全不需要理解容器格式**。`.psu`、`.max`、`.PSV`、PCSX2 的 memcard、
甚至一张 8 MB 记忆卡镜像，只要能找到那 12 个字节，就能读出徽章。

**代价**（三条，都要记住）：
1. 搜索是**子序列**匹配而不是子串匹配（失配只把计数器清零，不要求 12 字节相邻）
   ⇒ 容器里若散落着这些字节，可能定位到错的地方（限制问题 1）；
2. 一个文件**只处理一个徽章块** —— 它不枚举、不遍历。一个存档里 8 个徽章要分别喂 8 次；
3. **`isLR` 只看文件大小**（`size == 0x4420`）⇒ **容器里的 LR 存档一定会被当成非 LR 解析**
   （图像偏移取 `0x24` 而非 `0x4`、还多做一次乱序重排）⇒ 结果全错。
   所以 LR 必须喂裸 `dataX`。

## 三、★ 真实存档实测验证

**这一步把本目录从"相对官方工具正确"提升到了"相对真实游戏数据正确"。**

样本来源：GitHub 公开存档集合 [`bucanero/apollo-saves`](https://github.com/bucanero/apollo-saves)
→ `PS2/SLUS20644/00000001.zip`，其 README 标注为
**`BASLUS-20644E02: AC3SL Emblem No.3`**（Silent Line 的第 3 个徽章存档）。

文件是一个 **`.PSV` 容器，56,216 字节**（apollo 导出的格式，头部带 `\0VSP` 与
`www.bucanero.com.ar` 字样）。本目录把它收在 `testdata/real/`：

| 文件 | 大小 | 说明 |
|---|---|---|
| `testdata/real/BASLUS-20644E02_AC3SL_Emblem3.PSV` | 56,216 | 原始 `.PSV`，SHA256 `18DA0D78…CE62` |
| `testdata/real/BASLUS-20644E02_rawblock.raw` | 17,472 | 切出来的裸徽章块（`0x4440`） |
| `testdata/real/BASLUS-20644E02_extracted.png` | 3,982 | 提取出的徽章图 |

### 实测结果

```
魔数定位          : 0x154（全文件只有这一处）
12 字节魔数        : 20 44 00 00 20 44 00 00 00 40 00 00        ✅ 逐字节相符
头部三个 u32LE     : 0x4420  0x4420  0x4000                      ✅ 与推导一致
校验字节           : **18/18 段全部通过**（本实现的独立判据 verify_checksums，末段验真实位置 0x4435）
不透明色 alpha     : 所有在用调色板项都是 `xx xx xx 80`            ✅ 证实 0x80 约定
调色板 0 号项      : 00 00 00 00                                 ✅ 透明项固定占索引 0
乱序置换           : 索引 9 → 槽 17、10 → 槽 18                   ✅ 与公式吻合
用到索引数         : 102 个（范围 0..252）
暗含的透明像素     : 10,922 / 16,384 = 66.7%
```

### 双向逐像素比对

| 比对 | 结果 |
|---|---|
| 本实现提取 vs **官方 `acet.exe`** 提取 | **65,536 字节全部相同** ✅ |
| 裸 `0x4440` 块 vs `.PSV` 容器（官方 exe 各读一次） | **逐像素一致** ✅ |
| 本实现往真实存档注入自制图 → 官方 exe 读回 | **逐像素一致** ✅ |

### 提取出来的是什么

一朵**正立**的红玫瑰（红花瓣 + 绿茎叶），是玩家自绘的徽章。
这同时说明**读出方向没有镜像问题**（zk306 的 LR 工具曾要求输入"预先水平翻转"，
MLR 也修过"左右镜像"——那是它们自己的管线问题，不是格式要求）。

⇒ **`02-存档格式规范.md` 里原先标 `[未观测]` 的"头部 0x0C..0x23 那 24 字节"，现在有观测了：**

```
真实样本 0x0C..0x23：
  00 00 00 00 00 00 00 00 00 | a1 30 dd 85 ab 07 80 60 | 00 00 00 00 00 00 00
  └──── 0x0C..0x14 全 0 ────┘ └── 0x15..0x1C 八个非零字节 ──┘ └── 0x1D..0x23 全 0 ──┘
```
`0x15..0x1C` 那 8 个字节**含义未知**（可能是存档序号 / 时间戳 / 校验），
它落在第 0 段校验范围内，所以**改动它必须重算校验**。
`[未观测-含义]`：只见过一个样本，不敢下结论。**这也说明：不同存档这段大概率不同，
自己实现时不要假设它是 0。**

### ★ 样本②：真实 Last Raven（从**用户自己的记忆卡**只读取出）

原先本目录把"LR 一个真实样本都没有"列为**最大的空白**。现已补上 ——
来源就是本工作区自己的 PCSX2 记忆卡（用 `AC3_CN\tools\30-存档\61_mc_survey.py`
的 `Card` 类**只读**读取，**未向记忆卡写入任何字节**）：

```
记忆卡 : C:\Users\M\Documents\PCSX2\memcards\Mcd001.ps2
根目录项 #13  BISLPS-25462EMB      ← BISLPS-25462 = AC:LR 日版
   ├ static.ico          28,110 B
   ├ data0               17,440 B  ← ★ 真实 LR 徽章（用户只存了 1 个）
   ├ icon.sys               964 B
   └ BISLPS-25462EMB         32 B
已取出 → ../testdata/real/BISLPS-25462EMB_data0.raw
```

| 检查 | 实测 | 结果 |
|---|---|---|
| 文件大小 | 17,440 = `0x4420` | ✅ 判定为 LR |
| 校验字节 | **18/18 段通过**（LR 种子 `0xB8` + 末段校验位 `0x4415`） | ✅ |
| 与官方 `acet.exe` 比对 | **65,536 字节全同** | ✅ |
| 提取结果 | 一个**完全不透明**的紫蓝色恶魔脸徽章（128×128 满幅） | — |

⇒ **LR 路径（`0x4420` / 图像偏移 `0x4` / 无调色板乱序 / 种子 `0xB8` / 末段校验位 `0x4415`）
全部在真实数据上成立。**

★ 这份样本还纠正了一个格式误解：**"透明 = 索引 0" 是错的**。
真相是**透明与否只看调色板项的 `alpha == 0`**：

```
LR  data0    palette[0] = 00 00 00 40   ← alpha=0x40 ≠ 0 ⇒ 索引 0 是**不透明深色** ⇒ 全图 0 透明
SL  E02      palette[0] = 00 00 00 00   ← alpha=0       ⇒ 索引 0 透明，10,922 px 透明
```
"索引 0 留给透明"只是**写入端**（`acet`）的约定。另外 LR 那份的 alpha 是 **`0x40`**
而不是 `0x80` ⇒ **alpha 取值不止 0/`0x80`**（因"非 0 即不透明"，显示不受影响）。
详见 `02-存档格式规范.md` §五 与 `../../_selftest/02-真实存档验证.md` §四。

## 四、上游**不**做的事（做自己的 GUI 前必须知道）

| # | 不做的 | 后果 / 你要补的 |
|---|---|---|
| 1 | **不解析 PS2 记忆卡文件系统**（8 MB 镜像、簇链、ECC） | 不能"打开记忆卡 → 列出所有徽章存档" |
| 2 | **不解析 PCSX2 的 memcard 格式** | 同上；PCSX2 用户得先 Convert 成文件夹 |
| 3 | **不解析 `.psu` / `.max` / `.xpo` / `.sps` / `.xps` 的结构** | 只能靠魔数搜索"碰"; 也**不会更新容器的外壳校验** ⇒ 改完的 `.psu` 可能被存档工具拒收 |
| 4 | **不处理碎片** | 记忆卡上存档数据可能是链式簇；若在镜像里不连续，魔数搜索找到的块是**残缺**的 |
| 5 | **不枚举、不批量** | 一个文件一个徽章；8 个徽章手动 8 次 |
| 6 | **不区分存档类型** | `E##`（徽章）和 `S##`（出击存档）它一视同仁，只要大小对就硬写 |
| 7 | **不校验"这到底是不是徽章存档"** | 任意 17,472 字节的文件它都会照写不误 |

★ 第 3 条尤其要注意：**它把整个文件读进来、只改内部徽章块、再原样写回**，
容器外壳不会被拆掉，但外壳自己的校验/长度字段**不会更新**。
本目录的真实样本是 `.PSV`，我们**只做了读取**，没有回写 `.PSV`
⇒ `[未观测]`：改过的 `.PSV` 能不能被 apollo/PCSX2 接受，没验过。

## 五、存档命名规则（已确认）

| 作品世代 | 形态 | 例子 |
|---|---|---|
| AC2 → Nine Breaker | 一个文件一个徽章，`BASLUS-<游戏码>E<槽号>` | `BASLUS-20644E02` = SL 的第 3 个徽章存档 |
| 同上（出击/剧情存档） | `BASLUS-<游戏码>S<槽号>` | `BASLUS-20644S00` / `S03` |
| **Last Raven** | 一个目录 `BASLUS-21338EMB`，里面 `data0` … `data7` 共 8 个徽章 | 必须喂**裸 `dataX`** |

★ **`E##` 与 `S##` 的区别已经定案**（不是猜的）：
`apollo-saves` 的 Silent Line 页把 `BASLUS-20644E02` 标为 **"AC3SL Emblem No.3"**、
把 `BASLUS-20644S00`/`S03` 标为 **"SORTIE"**（出击）存档；AC3 页则只有 `S00`。
⇒ **`E##` = 徽章槽，`S##` = 出击/剧情存档。**
（这解决了本工作区 `ACSL_CN` 笔记里 `BASLUS-20435S00` 与上游 README 的 `E00` 那个分歧。）

### ★ 本工作区的记忆卡工具只做了 `S##`，没做 `E##`
这一点很关键，别搞混（用户 2026-10-04 明确指出）：

| | 覆盖 | 说明 |
|---|---|---|
| `AC3_CN\tools\30-存档\`（**27 脚本**）・`ACSL_CN\tools\30-存档\`（2 脚本） | **`S##` 出击存档** | 做的是**美↔日版格式转换**：目录名、`icon.sys` 标题、数据文件；外加完整的记忆卡文件系统（超块 / FAT / 簇链 / ECC） |
| — | **`E##` 徽章存档** | ❌ **零覆盖** —— 在 `*存档*.py` 里搜 `E00\|E01\|E02\|EMB\|emblem\|徽章` ⇒ **0 命中** |

⇒ 两边正好互补：**记忆卡层（第 1/2 层）已有，徽章编解码（第 4 层）是本目录新做的**
（详见 `../02-参考资料/02-与本工作区的关联.md` §五）。

### Last Raven 的目录名也跟着区域走

LR **日版**的徽章目录是 **`BISLPS-25462EMB`**（`BISLPS-25462` = SLPS-25462 = LR 日版），
里面是 `data0` … `data7`。
★ 本目录的真实 LR 样本就是从用户卡上这个目录取的（见 §三）。
上游 README 只提了美版的 `BASLUS-21338EMB` —— **日版不叫这个**，这是上游没覆盖到的。

### ★★★ `E##` 存档目录：`ICON` 里**烧着徽章快照**，而记忆卡画面显示的是它

`E##` 存档目录的形状与 `S##` 一样，**三个文件**：

```
BISLPS-25169E01/            ← 目录名 = 存档名
  ├ BISLPS-25169E01  17,472 B   ← 徽章数据（本文档 §二/§三 那个 0x4440 块）
  ├ AC3SLE.ICO       37,440 B   ← 图标（NX 是 ACNEXUSE.ICO，同尺寸）
  └ icon.sys            964 B   ← PS2 存档元数据（标题、图标名、槽位号）
```

★★ **`*.ICO` 的尾巴 0x8000 字节 = 128×128 的 16 位（BGR555）徽章贴图**（实测定案）：

```
ICO 布局 = [0x1240 字节  头部 + 3D 模型] + [0x8000 字节  128×128 16bit BGR555 贴图]
           且 0x1240 + 0x8000 == 文件长度 37,440 —— **贴图正好是文件尾巴**
像素编码 = 索引 0 → 0x0000（背景）；其余 = (r>>3) | ((g>>3)<<5) | ((b>>3)<<10)
判据     = SL 的 MIRAGE：ICO 贴图与"由存档数据渲染出的 BGR555"**逐像素 83.7% 完全相同**，
           且 ICO 里 =0 的像素数（10,076）≈ 徽章的背景像素数（10,077）
```

#### ★★ 关键行为：**记忆卡画面显示的是「存档数据」渲染出的徽章，不是 `ICO`**

> ⚠ **本节早先的结论（"缩略图就是 ICO 尾部那张贴图"）已被实机推翻**（2026-10-04 判别卡），
> 保留在此作为记录：**缩略图由存档数据渲染**。
> 判别实验：把 `E00` 的 **ICO 尾部贴图画成红蓝棋盘格、存档数据不动** ⇒ 缩略图**仍是正常 MIRAGE**；
> 把 `E01` 的**存档数据**反色、**ICO 不动** ⇒ 缩略图**变成反色**。
> ⇒ 缩略图这条路径**读的是数据文件**，`ICO` 那张贴图另有用途（可能就是 PS2 BIOS 浏览器用的）。

由此得到的实用结论：

| 玩家看到的东西 | 数据来源 |
|---|---|
| **记忆卡画面上的徽章缩略图** | **存档数据文件**（游戏自己渲染） |
| **真正 load 进游戏用的徽章** | 同一个**存档数据文件**；出错才是 `破損ファイル` |
| `ICO` 尾部那 `0x8000` 贴图 | **不是**缩略图来源（用途待查）`[未观测]` |

⇒ **改徽章只需要改存档数据文件**（不必碰 `ICO`），比原先以为的少一件事。

★ 顺带解释了之前的困惑：改完数据后缩略图**没变**，是因为数据**被游戏拒绝**（`破損ファイル`）——
游戏在那一格显示的是**兜底图标**（看起来像 MIRAGE 的样例徽章），不是我们写进去的图。

★ LR 与 SL/NX 在这一点上一致：都是**由数据渲染**。
（LR 的 8 格在**同一个** `BISLPS-…EMB` 目录里、没有各自的 ICO；SL/NX 是**每个徽章一个独立存档目录**。）

### `icon.sys` 里两个有用的字段

| 偏移 | 内容 | 实测 |
|---|---|---|
| `0xDF` | ★ **槽位号** | SL：`E00`=0、`E01`=1 ✓；NX 五个槽**全是 0** ❌（见 §十二「记忆卡的坑」） |
| `0xC0..0x103` | 标题（SJIS，68 B） | NX = `ＡＣＮＥＸＵＳ　徽章　Ｎｏ．１`；SL 是乱码但**不影响加载** |
| `0x104..` | 图标文件名 | `AC3SLE.ICO` / `ACNEXUSE.ICO` |

★ `0xDF` 落在标题字段**字符串结束之后的填充区**（第 31 字节）。
★ **标题里的 `Ｎｏ．Ｘ` 不跟槽号走**（NX 五份全是 `Ｎｏ．１`）⇒ 判据是 `0xDF`，不是标题。

> ### ⚠ 改标题时**必须先写标题、最后写 `0xDF`**（2026-10-04 本目录自己踩到）
>
> 因为 `0xDF` **就在标题字段内部**（`0xC0..0x103` 的第 31 字节），
> 一个自然的写法是"先把整段标题区清零、再写新标题"，而这一步会**顺手把刚设好的槽位号抹回 0**
> ⇒ NX 五槽又全变 0 ⇒ **进徽章画面直接卡死**。
> 正确顺序：① 写 `0x06` 长度；② 清零并写新标题；③ **最后**写 `0xDF`。
> 写完务必断言 `icon.sys[0xDF] == 期望槽号`。
> （脚本 `../../_selftest/write_lrtest2.py` 里就带着这条断言。）

> ### ⚠ 实机验证前**必须先确认模拟器实际把哪张卡插进了哪个槽**（2026-10-04 的教训）
>
> 游戏里那个徽章画面显示的是**当前浏览的那个 slot 上的卡**，标题会写 `MEMORY CARD slot 1` / `slot 2`。
> 但"某个 slot 上到底是哪张卡"**不等于**你在「设置 → 记忆卡插槽」对话框里选的那张：
> PCSX2 v2.x 还有一层 **每游戏设置**（`gamesettings\<序列号>_<CRC>.ini`），**它覆盖全局设置**。
>
> 本机实测：`SLPS-25462_FEBEC38B.ini`（LR 日版）里钉了 `Slot2_Filename = Mcd001_embdata2.ps2`，
> 于是对话框显示 `Slot 2 = Mcd001_TEST.ps2`，而 LR 读的一直是源卡 —— 换卡/冷启动/退回主界面**全都不变**，
> 本目录因此白绕了一整轮（先误判成"游戏在启动时建列表"，再误判成"缓存"）。
> **用户当时就断言"一定是记忆卡的问题"，是对的。** 完整经过 → `../../_selftest/04-末段校验差一字节.md` §十四.5；
> 问题条目 → `07-限制与已知问题.md` 问题 23。
>
> ★ **硬规则**：

## 七、`dev` 分支的 PS1 记忆卡支持（未发行，仅源码）

这是本仓库**唯一**真正"读记忆卡"的代码，而且**从未发行、也没编译产物**。
源码：`git show origin/dev:acet/acet.cpp`（第 229–447 行）。

### 记忆卡与目录

```
PS1 记忆卡 = 128 KB = 16 块 × 0x2000
  块 0            = 目录（"MC" 头）
  块 i (1..15)    = 存档槽；每个目录项 0x80 字节，存档名在 +0x0A，20 字节
```

* `isPS1Save()`：文件**前两字节**是 `'S','C'` 或 `'M','C'` 就认。
  `MC` = 整张记忆卡镜像；`SC` = 单个存档导出（`.mcs`）。
* `ListPS1MCBlocks()`：**要求前两字节是 `MC`**，然后读 `0x80*i + 0x0A` 处 21 字节名字，`i = 0..15`。
* 上游 CLI 提示原文：*"The memory card block number 1-14. 0 is reserved and
  **emblem saves use 2 blocks**. The emblem slot in the save 0-6.
  Emblem saves have 7 slots for emblems."*

⇒ **一个 PS1 徽章存档占 2 块 = 0x4000**，里面有 **7 个徽章槽**。

### 一个 2 块存档的内部布局（★ 本目录推导，与源码行为一致）

```
块起点 +0x000  .. +0x1FF   存档头（0x200 字节）
块起点 +0x200  .. +0x203   4 字节校验（32 位）
块起点 +0x204  ..          **槽 0** 的数据开始
                           7 个槽 × 0x820 = 0x38E0，到 +0x3AE4
每槽 0x820 字节：
      +0x000 .. +0x01F   调色板 32 字节 = 16 项 × 16 位 5:5:5
      +0x020 .. +0x81F   像素 2048 字节 = 64×64 @ 4bpp
      （每槽 0x814 有效 + 12 字节余量）
```

★ **槽定位公式**（上游写成 `0x2000*block + 0x820*slot` 然后再 `+checksumOff`，
因为 `0x820*1 + 0x204 == 0x204 + 0x820`，所以对每个槽都成立）：

```
槽 k 的数据起点 = 0x2000 * block + (isMOA ? 0x184 : 0x204) + 0x820 * k
                  block ∈ 1..14，k ∈ 0..6
```

### 4bpp 打包与颜色

```
打包：emblemBytes[i/2] = (pixel[i+1] << 4) | (pixel[i] & 0x0F)     ← 低半字节在前
解包：low  = byte & 0x0F   → 像素 i
      high = byte >> 4     → 像素 i+1
颜色：16 位 = r5 | (g5 << 5) | (b5 << 10)，存成两字节 (低字节, 高字节)
      r = byte0 & 0x1F
      g = ((byte1 & 0x03) << 3) | (byte0 >> 5)
      b = byte1 >> 2                     ← 三通道各 5 bit，标准 PS1 15 位色
透明：调色板**索引 0** = 透明（alpha 0），其余一律不透明
颜色数：**安全上限 15 色 + 透明**（上游 `> 16` 的差一 bug 见 §九）
```

### 校验（32 位，与 PS2 的 8 位完全不同）

```
校验位 = 0x2000*block + (isMOA ? 0x180 : 0x200)，4 字节 LE
覆盖   = 校验位之后 0x38E2 字节
算法   = ( -( sum(这 0x38E2 字节) + 0x38E2 ) ) 按 32 位写回 LE
```

### Master of Arena 是特例

* 判定方式：**看存档名** —— `ListPS1MCBlocks()` 里名字等于 `BASLUS-01030Z` 就是 MoA；
* 差异：校验偏移从 `0x200` / 写数据偏移 `0x204` 变成 `0x180` / `0x184`。

## 八、⚠ PS1 校验：两个独立来源**互相矛盾**（未决）

这是本目录**唯一一个明确标为"未解决"**的技术分歧，你必须知道它存在。

| 项目 | `acet` 的 `dev` 分支 | `alerner-6502/PSX-Emblem` |
|---|---|---|
| 语言/年份 | C++，2025，**未发行未测试** | C，2019，独立项目 |
| 覆盖 | AC1 / Project Phantasma / Master of Arena | 同 |
| 校验字段偏移 | `0x200`（AC1/PP）、`0x180`（MoA） | 512 / 512 / 384 = `0x200` / `0x200` / `0x180` ✅ **一致** |
| 校验覆盖范围 | 校验位之后 **0x38E2** 字节 | 起点 560 / 560 / 432，长度 **3040 / 3232 / 3240** |
| 算法 | 一律 `-(sum + len)`（二补数） | **只有 MoA** 才 `sum += 0xCA8; sum = -sum`；**AC1/PP 写原样的正和** |
| 图像定位 | 槽起点 + `0x204`/`0x184`，槽步进 `0x820` | **每作不同**：块内偏移 `{1080, 1272, 1152}` + `slot * 8192` |
| 调色板 | 从存档里读（16 项） | **硬编码 16 色**（索引 0 透明 + 15 色固定表） |

**能对上的**：校验字段偏移（`0x200` / `0x180`）、MoA 是特例、64×64 / 4bpp / 16 色 / 索引 0 透明。
**对不上的**：校验覆盖范围与算法、图像定位模型。

两端都不用 `0x820` 槽步进这一点尤其可疑 —— 说明两者对"一个存档里 7 个槽怎么排"
的理解**至少有一个是错的**。（`dev` 的 `parseArgs` 也承认
`ModifySavePS1()` 把 CLI 传来的块号/槽号丢掉了，硬编码成 `(1, 0)`。）

⇒ **结论：PS1 徽章格式目前没有可信版本。要动手前必须先拿真实数据定案。**

### 定案怎么做（成本很低）

```
1. 拿一张真实的 AC1 / PP / MoA PS1 存档（.mcr / .mcd，128 KB）
   —— GameFAQs 的 AC1 存档页里有带"pixel perfect emblem"的，
      格式是 DexDrive 的 131 KB 原始卡镜像；也可用 armouredcoreuniverse 的存档库
2. 用 PSX-Emblem（开源，有源码）改一次徽章 → 得到"改前 / 改后"两份卡
3. 逐字节 diff → 差异区就是真实的"徽章数据 + 校验"范围
4. 用这个范围去反推校验算法（对改后数据求和，看与卡上值的关系）
5. 拿结论同时校正 acet `dev` 与 PSX-Emblem 两边的说法
```
★ 这条路的产出会**同时**修正两个开源项目 —— 值得单独记一笔。

## 九、PS1 侧上游已知的两个小坑

1. **颜色数差一**：`if (palette_map.size() > 16)` —— 与 PS2 侧同一个毛病，
   第 17 项（索引 16）会被放进来，4bpp 装不下 ⇒ 高半字节移位后截断成 0。
   **安全上限 = 15 色 + 透明。**
2. **`.mcs`（`SC` 头）路径疑似少算 0x200**：`if (header[0] == 'S') block = 0;`
   之后用 `0 + 0x820*slot + 0x200` 定位，但 `.mcs` 文件本身还有 **0x200 字节的文件头**，
   所以算出来会落在存档头而不是校验位/调色板。
   而且 `ListPS1MCBlocks()` 又**硬要求 `MC` 头** ⇒ 实际上 CLI / GUI 的 PS1 路径
   **只支持整张记忆卡镜像**，`.mcs` 那条路基本是死代码。`[源码直读]`

## 十一、`.psu` 容器结构（做第 2 层时要用的）

据 [ps2savetools 的 .psu 文档](https://www.ps2savetools.com/documents/ps2-save-game-format-for-ems-adapter-psu/)
（**本目录未用真实 `.psu` 验证过，只作线索**）：

```
每个文件系统条目：
  32 字节头
     +0x00  2 字节  条目 ID：0x2784 = 目录/自身/父目录项；0x9784 = 普通文件；0x27A0 = PS2 系统存档
     +0x05  4 字节  目录项→文件数；文件项→文件大小（**高位在前**）
     +0x09  8 字节  创建日期
     +0x10  2 字节  起始扇区
     +0x19  7 字节  修改日期
  +0x20  32 字节全 0
  +0x40  448 字节条目名（右侧补 0）
  之后是文件内容，再补 0 到 1024 字节的整数倍
整体布局：[目录条目(文件数 = X)][.][..][文件 3]…[文件 #X]
```

⇒ 所以"从 `.psu` 里取徽章文件"是**解析条目链**，不需要魔数搜索 ——
比上游那招可靠。**但也要注意**：写回时必须同步更新目录条目的文件大小、
并且 `.psu` 若有自己的校验，得一起更新（本目录未验证 `.psu` 是否有校验）。

### ⚠ 记忆卡读写的三个坑（本目录实测踩到的）

| # | 坑 | 细节 |
|---|---|---|
| 1 | **`mode & 0x2000` 不是"目录"位** | 本卡实测：**目录 = `0x8427`、文件 = `0x8497`，两者的 bit13(0x2000) 都是 0**。`61_mc_survey.py` 里的 `is_dir = bool(mode & 0x2000)` 因此**恒为 False**，别用它判目录（本目录的 `dump_card_emblems.py` 就因此漏扫了一整轮）。<br>★ **2026-10-04 用 `_selftest/check_dirent_bits.py` 复核**（4 张证据卡共 **450 个 dirent**，按**结构证据**判定 —— 该簇能否解析出 `.` / `..` 表）：<br>　**目录** = `0x8427`（211 个）+ `0xA426`（4 个，根目录的 `.` 项）；**文件** = `0x8497`（235 个）⇒ **两类取值完全不相交**。<br>　逐位：**bit4 / bit5 / bit7** 三个位都能 100% 分离；**bit13 在目录里只有 1.9%**（就是那 4 个根 `.`）。<br>⇒ 最稳判据是**结构**（能不能解析出 `.`/`..` 表），其次才是 mode 值；<br>　**别只按名字判**：LR 的 `BISLPS-25462EMB` 目录里有**一个文件也叫 `BISLPS-25462EMB`**（32 字节头），按名字会误判成目录。 |
| 2 | **像素区与调色板区中间夹着校验字节** | 每 `0x3FF` 逻辑字节 1 个校验字节 ⇒ 任何"连续切片"式统计都会在第一个校验字节之后**整体错位**。必须**逐像素 / 逐字节**走 `offset_index`。（本目录的 `acet_cli.py --info` 早先就是连续切片，"索引 0 的像素数"因此少数了 16 个。） |
| 3 | **`dirents(cluster, count)` 的 `count` 要用「上层目录条目里的 `length`」** | 不是 `.` 项的 `length`（子目录里它恒为 0），也不是"簇数 × 2"。而且**声明项数可能滞后**：实测 EMB 目录声明 6 项时里面已有 7 项，按声明数读会**漏掉最后一个文件**。 |
| 4 | **ECC 有两版公式，且 PCSX2 根本不校** | 页备用区 ECC 里 `lp0` 要用 `(~i) & 0x7F`（**不是** `& 0xFF`）：4 张证据卡实测 `& 0x7F` 匹配 **11,431 页**、`& 0xFF` 匹配 **0 页**。<br>⚠ 因为 PCSX2 不校验 ECC，**用错公式在实机上也看不出来** —— 只有拿真卡 dump 逐页反解才判得出（TS 移植时就是靠这个抓到的）。 |
| 5 | **FAT 的"空闲"标记是 `0x7FFFFFFF`，不是 `0xFFFFFFFF`** | `0xFFFFFFFF` 是**单簇文件的链尾**（= `0x80000000 \| 0x7FFFFFFF`）⇒ **不能靠 FAT 值判空闲**；要用"可达簇集合 + 系统区"扫描法（`write_data2_inverted.py` 用的就是它，且分配起点原样保留 `aoff+2`）。 |
| 6 | **dirent 名称区 32 字节的填充是 `00`，不是 `FF`** | 真卡实测：`名字 + 00 + 一路 00`。克隆 dirent 时必须整块覆盖这 32 字节（先 `fill(0xFF)` 再只覆盖名字长度会写出与真卡不同的字节）。 |
| 7 | **项数记在「根目录里那个目录 dirent 的 `length`」上** | 子目录自己 `.` 项的 `length` **恒为 0**。所以 `dirCount()` 只对根目录可信；新建文件后要更新的是**根目录条目的 length**（`write_data2_inverted.py` 就是把 `BISLPS-25462EMB` 的 length 7→8）。 |

⇒ ★ 第 2 条是**通用教训**：这个格式里"逻辑下标 ≠ 物理偏移"，凡是**按字节范围**做的统计/切片，
都要先问一句"这段里有没有夹校验字节"。

★ 结合这些，"真实存档验证"这一步是可以继续做深的 ——
每多一个真实样本，就把 §三 的结论从"n 个样本"推到"n+1 个"。**目前的账**：
