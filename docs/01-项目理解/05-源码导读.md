# 源码导读

上游源码一共 22 个文件，其中**真正含格式知识的只有 3 个**：
`acet/acet.h`（常量）、`acet/acet.cpp`（算法）、`acet-cli/main.cpp`（用法）。
其余是 wxWidgets 界面代码和 LodePNG 第三方库。

阅读顺序建议：`acet/acet.h` → `acet/acet.cpp` → `acet-cli/main.cpp` → 有需要再看 GUI。

## 一、`acet/acet.h`（39 行，全部常量）

```c
const unsigned kSaveSize     = 0x4440;  // 非 LR 徽章存档大小
const unsigned kLRSaveSize   = 0x4420;  // Last Raven 徽章存档大小
const unsigned kImageOffset  = 0x24;    // 非 LR：图像相对徽章块起点的偏移
const unsigned kLRImageOffset= 0x4;     // LR  ：同上
const unsigned kImageWidth   = 128;
const unsigned kImageHeight  = 128;
const unsigned kNumPixels    = 0x4000;  // 128*128
const unsigned kPaletteSize  = 0x400;   // 256 色 * 4 通道

const uint8_t kEmblemHeader[12] = {
    0x20, 0x44, 0x00, 0x00, 0x20, 0x44, 0x00, 0x00, 0x00, 0x40, 0x00, 0x00
};
```

★ `kEmblemHeader` 拆成三个 u32LE 就是 `0x4420 / 0x4420 / 0x4000`
—— 前两个正好是 **LR 存档大小**。这是理解"两条布局其实是同一个东西"的钥匙，
详见 `02-存档格式规范.md` §一。

注意 `acet.h` 里**没有**任何关于校验和偏移的常量：`0x98 / 0xB8 / 0x35 / 0x15 / 0x3FF`
全是硬编码在 `acet.cpp` 里的字面量。本目录的 Python 实现把这些推导成了具名常量
并断言与字面量相符（`tools/acet_format.py` 的 `_selfcheck()`）。

### `InjectImage()` 的流程（最值得精读的一段）

```c
bool isLR = save.size() == kLRSaveSize;      // ← 布局判定只看文件大小
size_t emblem_offset = FindOffset(save);
size_t image_offset  = isLR ? 0x4 : 0x24;

// ① 建调色板：按颜色首次出现顺序分配索引，透明项固定占 0
unordered_map<uint32_t,int> palette_map = { {PackColor(0,0,0,0), 0} };

for (每 4 字节 = 一个像素) {
    uint32_t c = 0;
    if (image[i*4+3] == 0xFF)                 // 只有"完全不透明"才保留颜色
        c = PackColor(r, g, b, 0x80);         // 注意 alpha 存 0x80，不是 0xFF
    if (c 是新颜色) {
        if (palette_map.size() > 256) throw;  // ⚠ 差一，见 07-限制与已知问题.md
        palette_map[c] = palette_map.size();
        for (channel = 0..3)                  // 写调色板那一项
            save[OffsetIndex(image_offset + kNumPixels + idx*4 + channel,
                             emblem_offset)] = (c >> (24 - channel*8)) & 0xFF;
    }
    int p = isLR ? palette_map[c] : UnscramblePalette(palette_map[c]);
    save[OffsetIndex(i + image_offset, emblem_offset)] = p;   // 写像素索引
}

// ② 重算全部校验字节
uint8_t sum = isLR ? 0xB8 : 0x98;            // ★ 首段有"魔数"种子
for (i = 0; i < (isLR ? 0x4420 : 0x4440); i++) {
    if ((i+1) % 0x400 == 0) {                // 每个物理块末尾写校验
        sum = ~(sum + 0x3FF) + 1;            // = -(sum + 数据字节数)
        save[i + emblem_offset] = sum;
        sum = 0;                             // 段间不累积 ⇒ 各段独立
    } else sum += save[i + emblem_offset];
}
// ③ 末段：先把"文件里原有的校验值 + 1"从累加和里减掉，再写
sum -= (save[prev_check + dangling] + 0x01);
save[prev_check + dangling] = ~(sum + dangling) + 1;   // ★ = 0x4434 / 0x4414 —— 早了一格，见下
```

★★ **两个反直觉的点，抄代码时最容易错**：

1. **首段种子不是 0** —— 上游注释原文：*"Basically ~(sum + len) + 1 but the first one
   has a magic number added to sum"*。种子 `0x98`（非 LR）/ `0xB8`（LR）。
   漏掉它，第一段校验就永远是错的。
2. **`dangling`（`0x35` / `0x15`）就是末段的数据字节数（53 / 21）**，数据从 `0x4400` 开始。
   ★ **2026-10-04 更正**：本目录原先把它解释成"末段数据字节数 **+ 1**、好让校验位落在块尾"，
   那是**倒果为因**。真实情况是：上游把它当成"从上一个校验字节 `0x43FF` 起算的偏移"用
   （`prev_check + dangling` = `0x43FF + 0x35` = `0x4434`）⇒ **校验位写早了一个字节**，
   而 `0x4434` / `0x4414` 其实是 `palette[255].alpha`。正确的末段校验位是 **`0x4435` / `0x4415`**。
   只要尾部是游戏写的 `X 01 00*9`，这个错误写法与正确写法**恒等**（原地注入一直"能用"）；
   **从空白块造**存档时两式相差 `0xFF`，游戏判 `破損ファイル`。
   ⇒ 详见 `../../_selftest/04-末段校验差一字节.md` 与 `07-限制与已知问题.md` 问题 8。

### `ExtractImage()` 的三处关键细节

```c
bool isLR = save.size() == kLRSaveSize;

// ① 图像：逻辑下标 + 跳过校验字节
for (i = 0; i < 0x4000; i++) pixels[i] = save[OffsetIndex(image_offset + i, emblem_offset)];

// ② 调色板：alpha != 0 一律归一成 0xFF（存档里只有 1 bit 透明度）
for (i = 0; i < 0x400; i++) {
    uint8_t c = save[OffsetIndex(image_offset + 0x4000 + i, emblem_offset)];
    if (i % 4 == 3 && c != 0) c = 0xFF;
    colors[i] = c;
}

// ③ 索引 → 颜色：非 LR 要再过一次 UnscramblePalette
image[i*4+c] = isLR ? colors[pixels[i]*4 + c]
                    : colors[UnscramblePalette(pixels[i])*4 + c];
```

★ 注意 ③：**注入时重排了一次、提取时又重排了一次**。这不是笔误 ——
`UnscramblePalette` 是**对合置换**（做两次等于没做），两次相抵，结果正确。
自己重写时**两处都要保留**，只留一处会得到颜色全乱的徽章。

★ 顺带解释了 `FindOffset` 返回的 `emblem_offset` 为什么要一路传下去：
容器文件里徽章块不在 0 位置，`pixels[i]`、调色板、校验全都得跟着偏移。

## 三、`acet-cli/main.cpp`（134 行，命令行前端）

逻辑极简，没有参数解析库：

```c
if (argc == 2) {
    if (isPNG(argv[1])) ExitMessage("PNG detected without save file - ...");
    WriteImage(argv[1]);                    // 提取 → <存档名>.png
} else if (argc == 3) {
    b[0] = isPNG(argv[1]); b[1] = isPNG(argv[2]);
    if (b[0] && b[1])       ExitMessage("Both arguments are PNGs ...");
    else if (isPNG(argv[1])) ModifySave(argv[2], argv[1]);   // 顺序无所谓
    else if (isPNG(argv[2])) ModifySave(argv[1], argv[2]);
    else                    ExitMessage("Neither argument is a PNG ...");
} else {
    /* 打印用法，等回车 */
}
```

几个值得注意的点：

* **靠"文件头 8 字节是不是 PNG 签名"判断哪个参数是图**（`isPNG()`），
  所以参数顺序无所谓；两个都不是 PNG 就报错。
* `ModifySave()` 会**先把原文件写成 `<存档名>.backup`**，再原地覆盖存档
  （v1.0.0 时是另写 `-modified`，v1.0.1 起改成备份 + 原地写）。
* `WriteImage()` 的输出名是 `存档名 + ".png"`（v1.0.0 时叫 `output.png`）。
* ★ **所有错误路径最后都会 `cin.get()` 等回车**（`ExitMessage()`）。
  脚本化调用时必须把 stdin 接到空设备，否则会**永久挂住**。
  本目录的 `tools/selftest.py` 就踩过这个，用 `stdin=DEVNULL` 解决。

PNG 编解码全部委托 **LodePNG**（`acet-cli/LodePNG/`，MIT）。
`lodepng::decode()` 默认输出 RGBA8，所以 CLI 拿到的就是 128×128×4 字节。

### GUI 与 CLI 的**行为差异**（容易被忽略）

`MainFrame::InjectHelper()` 做的事比 CLI 多：

```cpp
int colors = 256;
if (!image.HasMask()) {
    if (!image.HasAlpha()) { image.InitAlpha(); colors = 255; }
    image.ConvertAlphaToMask();               // ← alpha 变成 1-bit mask
}
if (image.GetWidth() > 128 || image.GetHeight() > 128)
    image.Rescale(128, 128);                  // ⚠ 只缩"大于 128"的，小于 128 不处理
if (image.CountColours(colors+1) > colors)    // 超色就量化
    wxQuantize::Quantize(image, quantized, &pal, colors, 0, ...);
```

⇒ **GUI 能直接吃 JPG/BMP/GIF 和任意尺寸的图**（会自动缩放减色），CLI 不能。
⇒ GUI 走的是 `ConvertAlphaToMask()`（默认阈值 128），CLI 走的是"`alpha != 0xFF` 即透明"，
   **两者对半透明像素的处理不同**。
⇒ `image.GetWidth() > 128` 那个条件意味着**小于 128×128 的图不会被缩放**，
   接下来的循环仍按 0..127 取像素 ⇒ 越界读（见 `07-限制与已知问题.md` 问题 5）。

## 五、`dev` 分支多出来的 PS1 支持（未发行，仅源码）

`dev` 分支（头提交 `9073a7f`，2025-03-11）比 `main` 多 571 行，加在 `acet/acet.cpp` 尾部：

| 函数 | 作用 |
|---|---|
| `ExtractImageAC1(filename, isMOA, block, slot)` | 直接从整张 PS1 记忆卡里取 64×64 徽章 |
| `InjectImageAC1(filename, image, isMOA, block, slot)` | 写回去 |
| `ApplyChecksumAC1(filename, isMOA, block)` | PS1 侧的块校验 |
| `ListPS1MCBlocks(filename)` | 列出记忆卡 16 个块里的存档名 |
| `isPS1Save(filename)` | 头两字节是 `SC` 或 `MC` 就认 |

关键数值（**这些在本仓库之外没有公开资料**）：

```
定位：off = 0x2000 * block + 0x820 * emblemSlot      block 1..14，slot 0..6
      （block 0 是记忆卡目录，被显式拒绝；7 个徽章槽）
数据：checksum 4 B  →  palette 32 B（16 色 × 2 B）  →  图像 64*64/2 = 2048 B（4bpp）
      checksumOff = isMOA ? 0x180 : 0x200             ← Master of Arena 不一样！
校验：对 checksum 之后的 0x38E2 字节求和，加 0x38E2，取负，写回 4 字节 LE
```

作者自己在 `dev` 里留了一堆注释掉的调试输出和 `"Temp help message"`，
还在 `ModifySavePS1()` 里把 CLI 传进来的 `block`/`slot` 参数**丢掉不用**
（硬编码 `InjectImageAC1(savename, image, isMOA, 1, 0)`）—— 说明确实没收尾。

⚠ **订正（本目录自查发现的错误）**：早先版本的本页曾写"`ExtractImageAC1()` 里蓝色通道
`(palette[i*2+1] >> 2) * factor` 取到 6 bit 会溢出"—— **这是错的**。
实际位布局是每色 5 bit：`right = (g>>3) | (b<<2)`，`b` 最大 `31`（`image/8`），
`b<<2` 最大 `124`，`right` 最高位是 0 ⇒ `right >> 2` 恰好还原 5 bit 的 `b`，
`31 * 8 = 248` 不溢出。RGB 三通道都是 5 bit，是标准 PS1 的 15 bit 色。
（同类的"看着像 bug"要按位算完再说，不能凭直觉。）

⚠ 另一处**真的**差一：`if (palette_map.size() > 16)` 与 PS2 侧同一个毛病 ——
第 17 项（索引 16）会被放进来，而 4bpp 装不下 16 ⇒ 高半字节移位后截断成 0。
**PS1 实际安全上限 = 15 色 + 透明**。详见 `07-限制与已知问题.md`。

## 六、本目录对源码做了什么（以及没做什么）

* **没有改动上游一个字节**。`src/ac-emblem-tool/` 是原样 `git clone`，
  含全部 20 个提交、3 个分支、5 个 tag。`dist/` 里的二进制是原样下载的官方发行包。
* 新增的是**独立的一份**：`tools/acet_format.py`（零依赖参考实现）、
  `tools/acet_cli.py`（Python 命令行）、`tools/selftest.py`（与官方 exe 的交叉验证）。
  这份实现是**重写**而不是翻译，用的推导路径不同（例如校验分段是从格式定义反推的，
  不是照抄循环），因此两边的分歧能暴露问题 —— 事实上它第一次跑就抓出了
  本目录最初把"首段种子"和"末段偏移"写错的两处错误；
  后来又靠同一套独立判据（按格式定义推的 `segment_layout`，而不是照抄上游循环）
  暴露了**上游自己**的问题：末段校验字节写早了一个字节（`../../_selftest/04-末段校验差一字节.md`）。
