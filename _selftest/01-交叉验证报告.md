## 一、为什么要做交叉验证

只有一份实现的时候，"读写能往返"证明不了任何事 —— 读错和写错可以互相抵消。
单实现往返自洽，完全可以建立在一个**错误**的格式理解上。

本目录最初就是这么出错的：`acet_format.py` 第一版把

1. **首段校验的魔数种子**（`0x98` / `0xB8`）漏了，
2. **末段校验字节的偏移**算错（当成 `0x443F`，实为 `0x4434`），

结果自检"全部通过"（自己写、自己读、自己验，全自洽）。
是**上游校验循环的逐行直译**（`apply_checksums_upstream()`）第一次跑就报了两处不一致，
才把这两个错误挖出来。

> **★ 后记（2026-10-04，同一教训又发生了一次）**
> 上面第 2 条的"实为 `0x4434`"**本身还是错的** —— `0x4434` 不是末段校验位，而是
> `palette[255].alpha`；**真正的末段校验位在 `0x4435`**（LR 在 `0x4415`）。
> 因为把上游当权威，这个"少一个字节"的错误被照抄了下来，导致此后**所有非 LR 写入**
> 都被游戏判 `破損ファイル`；而交叉验证之所以一直"全过"，是因为上游从已有存档注入时
> 两套写法恰好奇异恒等（详见 `04-末段校验差一字节.md` §三）。
> ⇒ **"以上游为权威"只能证明"与上游一致"，不能证明"与游戏一致"**；
> 真正的权威是**游戏自己写的存档**，最强判据是"写入器能否逐字节复原真实存档"。
> 该判据已加入 `validate_writer.py`（10/10 通过）。

⇒ 所以本报告的核心不是"Python 实现能跑"，而是：**拿官方二进制当权威，
让两个独立实现互相证伪**。

## 二、验证方法

```
三种载体：
  [AC3]   非 LR 原始存档             BASLUS-20435E00.raw     0x4440 字节
  [LR]    Last Raven 原始存档        BASLUS-21338EMB_data0.raw  0x4420 字节
  [容器]  0x200 前缀 + 上述 AC3 存档  container_with_emblem.bin  → 走 12 字节魔数定位

四组方向（每组都要过）：
  A. 本实现写存档 → 官方读出来        → 逐像素比
  B. 官 方写存档 → 本实现读出来        → 逐像素比
  C. 本实现写 → 官方读 → 官方再写 → 本实现读（两轮交替往返）
  D. 官方写 → 本实现覆盖写 → 官方读    → 逐像素比（交替改写，最能暴露隐式状态）

另加：本实现写出的存档必须通过**独立判据** `verify_checksums()`；
      官方写出的存档也必须通过同一个独立判据；
      任何一方都不得改变存档大小。

测试图：128×128 索引色，A = 56 色、B = 41 色，左上角含全透明区域。
```

★ 注意 `verify_checksums()` 是**独立判据**：它按格式定义（分段 + `-(sum+len+seed)`）
从零重算，而不是把写入器的循环再跑一遍 —— 与上游那种"自己验自己"的写法不同。

```
总计 25 项，通过 25，失败 0
```

| 载体 | 断言 | 结果 |
|---|---|---|
| AC3 | 本实现写出的存档校验自洽 / 自读自写往返一致 | PASS |
| AC3 | [A] 本实现写 → 官方读 逐像素一致 | PASS |
| AC3 | [B] 官方写 → 本实现读 逐像素一致 / 官方产物校验自洽 | PASS |
| AC3 | [C] 写→读→写→读 交替往返一致 | PASS |
| AC3 | [D] 官方→本实现→官方 逐像素一致 | PASS |
| AC3 | 存档大小不被改写（17472 = 17472） | PASS |
| LR | 同上 8 项（存档大小 17440） | PASS |
| 容器 | 同上 8 项（大小 17984，徽章块起点 0x200） | PASS |
| 基础 | `acet_format.py` 内部自检全通过 | PASS |

### 对 `dist/v0.1/acet-cli.exe`（MSVC 构建，需要 VC++ 运行库）

```
总计 25 项，通过 25，失败 0
```

⇒ v0.1 包里那个 `acet-cli` 与 v1.0.2 的 `acet.exe` **行为一致**（与源码分析相符：
GUI 那批提交没有改 `acet/cli` 的格式逻辑）。

### `acet_format.py` 内部自检（`python tools\acet_format.py`）

```
[常量] DANGLING           = 0x35 (上游 0x35) OK
[常量] DANGLING_LR        = 0x15 (上游 0x15) OK
[常量] FINAL_CHECK_OFF    = 0x4434 (上游 0x4434) OK
[常量] FINAL_CHECK_OFF_LR = 0x4414 (上游 0x4414) OK
[常量] SEED               = 0x98 (上游 0x98) OK
[常量] SEED_LR            = 0xB8 (上游 0xB8) OK
[AC3] 空白存档校验 / 两种校验实现一致 / 往返 / 幂等 / 独立判据接受上游校验 —— 全 OK
[LR]  同上 —— 全 OK
[容器] 子序列定位 = 0x120 = 连续定位；往返一致；校验自洽
全部通过（0 项失败）
```

★ 其中"常量"那 6 行值得单独看：它们是**推导值 vs 上游字面量**的比对。
`0x35 / 0x15 / 0x4434 / 0x4414 / 0x98 / 0xB8` 这几个数在上游源码里是散落的魔数，
本实现改成从格式定义推导（`FINAL_CHECK_OFF = SAVE_SIZE - TRAILING - 1` 等），
再断言与字面量相等。这既证明推导正确，也让这些数字在文档里有了解释。
