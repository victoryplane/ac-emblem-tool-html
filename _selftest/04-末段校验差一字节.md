## 一、结论（一句话）

**上游 `acet` 把第 18 段（末段）的校验字节写早了一个字节。**
真实的末段校验字节在 `0x4435`（非 LR）/ `0x4415`（LR），上游写在 `0x4434` / `0x4414`；
而 `0x4434` / `0x4414` **根本不是校验位，是 `palette[255].alpha`**。

因为上游工具总是**在已有存档上原地注入**（那 11 字节尾巴被原样保留），
它的错误写法恰好与正确写法**恒等**，所以一直没暴露；一旦**从空白块造**存档
（尾巴为 0），两式就相差 `0xFF`，游戏判 `破損ファイル`。

> **★ 实机已确认（2026-10-04）**：修正后 `Mcd001_final.ps2` 的 **7 格（NX 5 + SL 2）
> 全部正常读取**，无一格 `破損ファイル`。**非 LR 写入打通。** 详见 §八。

## 二、真实末段布局

非 LR 与 LR 的第 18 段结构完全同构：

```
                     数据（dangling 就是它的长度）        校验   不参与校验的 10 字节
非 LR (0x4440)： [0x4400 .. 0x4434]  53 B  [@0x4435]  [0x4436..0x443F] = 01 00 00 00 00 00 00 00 00 00
LR    (0x4420)： [0x4400 .. 0x4414]  21 B  [@0x4415]  [0x4416..0x441F] = 01 00 00 00 00 00 00 00 00 00
                 ↑ 上一个常规校验字节在 0x43FF，数据从它**下一个字节**开始
```

三个关键点：

1. **`dangling`（非 LR `0x35`=53 / LR `0x15`=21）是"数据长度"，不是"偏移"。**
   上游把它当偏移用（`prev_check + dangling` = `0x43FF + 53`），少了那"下一个字节"的 1。
2. **`0x4434` / `0x4414` 是 `palette[255].alpha`。** 调色板的物理范围是 `0x4034..0x4434`
   （非 LR），槽 255 的 alpha 正好落在 `0x4434`。游戏对每一项的 alpha 都写 `0x80`
   （只有槽 0 是 `0x00`），所以这一格在**全部 10 份真实样本里都是 `0x80`**。
   ⇒ `FINAL_CHECK_OFF` 这个旧名字的语义是错的。
   （附带一个陷阱：`0x4400..0x4433` 是调色板最后 14 项的字节，这一段里 `0x43FF` 处跳过了
   一个校验字节，所以**槽边界不再与 4 字节对齐**；定位一律走 `offset_index()`，
   不要用连续切片。）
3. **校验之后的 10 字节 `01 00*9` 不参与任何校验**，但**不能留 0**。
   它是**游戏写下的字段**（初始版本的上游代码就是从源存档原样抄这 10 字节的），
   所以 `apply_checksums` 的策略是：**已有非零值就原样保留，只有从空白块造（全零）时才补
   `01 00 00 00 00 00 00 00 00 00`**。
   （它同时影响"两式是否恒等"：恒等的充要条件是 `sum(这 10 字节) = 1`。）

前 17 段完全没变：校验在 `0x3FF, 0x7FF, …, 0x43FF`，每段输入 1023 字节，
第 0 段带种子 `0x98`（LR `0xB8`），公式 `-(sum(数据) + 数据长度) & 0xFF`。

## 三、为什么上游"一直能用"——两套写法恒等

设 `S = sum(0x4400..0x4433)`，尾部 11 字节记作 `T = b[0x4435..0x443F]`。

| 写法 | 公式 |
|---|---|
| 上游（旧） | `b[0x4434] = -(S + sum(T) + 52) & 0xFF` |
| 真实（新） | `b[0x4435] = -(S + b[0x4434] + 53) & 0xFF` |

**当尾部形如 `X 01 00*9` 时 `sum(T) = X + 1`，两式恒等**（互为同一个方程的两条推论）：

```
把新式的 b[0x4435]（=X）代回旧式右边：
  -(S + (X+1) + 52) = -(S + X + 53)
新式给出  X = -(S + b[0x4434] + 53)
⇒ 旧式右边 = -(S - S - b[0x4434] - 53 + 53) = b[0x4434]   ✅ 左=右
```

- **原地注入**（上游工具的用法）：尾部是游戏写的 `X 01 00*9` ⇒ 恒等成立 ⇒ 能用。
- **从空白块造**（我们的用法）：尾部全 0，`sum(T) = 0 ≠ X + 1` ⇒ 两式相差 `0xFF` ⇒ `破損ファイル`。

★ 注意：只要尾部是 `X 01 00*9`，**`X` 取什么值都同时满足两式**。
所以新写入器可以放心地按真实式**算出** `X`；`0xCB` / `0xEB` 并不是"作品常量"。

## 四、数值证据

### 1) 10 份真实存档：两套写法都通过

```
BASLUS-20644E02_rawblock.raw   逐字节复原 ✅  真实写法 ✅  上游写法 ✅  尾部 78 01
BISLPS-25169E00/E01.raw        逐字节复原 ✅  真实写法 ✅  上游写法 ✅  尾部 cb 01
BISLPS-25338E00..E04.raw       逐字节复原 ✅  真实写法 ✅  上游写法 ✅  尾部 cb 01
BISLPS-25462EMB_data0/data1    逐字节复原 ✅  真实写法 ✅  上游写法 ✅  尾部 eb 01
```

"逐字节复原"= 把**新写入器**（`apply_checksums`）作用在真实存档上，输出与原文件
**完全相同**。这是最强判据：游戏的产物按定义就是"游戏认可的字节"，
我们的写入器必须收敛到同一个不动点。

### 2) 旧写法在新判据下暴露

```
旧式（尾部全零 + 上游写法）:  真实写法 ❌ seg17（文件=0x00，期望=0xFF）   上游写法 ✅
```

⇒ 与"游戏判破損"完全对应的字节级差异。

### 3) 12 个候选公式里只有 2 个全中，且它们是同一个方程

`check_tail.py` 对 10 份真实样本逐一验证了 A（上游式）、B（无尾巴）、C（真实式）、
D（链式）、E/F/G/H（整文件求和/XOR）等 10 个公式：**只有 A 与 C 命中 10/10**，
其余 0/10。而 A 与 C 的恒等性正是第三节的推导。

### 4) `X` 不是作品常量

| 来源 | 作品 | `X` |
|---|---|---|
| 用户记忆卡 | SL 日版（MIRAGE） | `0xCB` |
| 用户记忆卡 | NX 日版（CREST） | `0xCB` |
| 用户记忆卡 | LR 日版（恶魔 / 树） | `0xEB` |
| 第三方存档库 | SL 美版（玫瑰） | **`0x78`** |

`0xCB = -53`、`0xEB = -21` 只是因为这些存档的调色板尾部（槽 242..255）恰好让
`sum(0x4400..0x4434) ≡ 0 (mod 256)`；SL 美版玫瑰的未用槽 RGB 是一条渐变，
和不为 0，于是 `X = 0x78`。**它是算出来的校验值，不是常量。**

### 5) ★★★★★ 上游自己的 git 历史是第三条独立证据

`src/ac-emblem-tool` 的克隆里有完整历史。**最初的手工逆向版本**（初始提交 `0197b20`，
当时全部代码都在单文件里（现在的路径是 `src/ac-emblem-tool/acet-cli/main.cpp`，
早期提交里叫 `src/main.cpp`）写的是：

```cpp
const int kStrippedSize = kImageOffset + kNumPixels + kPaletteSize;   // 0x24+0x4000+0x400 = 0x4424
for (int i = 0, j = 0; i < kStrippedSize; i++, j++) {
    if (j % 0x400 == 0x3FF) {
        sum = ~(sum + 0xFF) + 1;
        if (j == 0x3FF) sum += 0x68;          // 首段的"魔数"
        outfile.write((char*)&sum, 1); sum = 0; j++;
    }
    outfile.write((char*)&buffer[i], 1); sum += buffer[i];
}
// The final checksum needs 202 added to it
sum = ~(sum + 0xFF) + 1 + 0xCA;
outfile.write((char*)&sum, 1);
outfile.write((char*)&buffer[kStrippedSize+1], 10);      // ★ 后面 10 字节从源存档原样抄
```

把它翻译成最终文件布局，可以完全对上：

| 项 | 初始版本 | 最终布局 |
|---|---|---|
| 常规段输出字节数 | `0x4424` 数据 + 17 个校验 | 到 `0x43FF` 共 17 个校验 |
| **末段校验的位置** | 循环结束后**紧跟最后一个数据字节**写 ⇒ `0x4424 + 17 = 0x4435` | **`0x4435`** ✅ |
| **末段校验的值** | `~(x + 0xFF) + 1 + 0xCA` = `-(x + 255 - 202)` = **`-(x + 53)`** | **`-(x + 53)`** ✅ |
| 之后 10 字节 | 从源存档**原样抄** | `01 00*9`（游戏写下的字段）|
| 总长 | `0x4435 + 1 + 10 = 0x4440` ✅ | 0x4440 ✅ |

⇒ **最初的逆向是精确正确的**，而且它揭示了两件事：
`0xCA = 202 = 255 − 53` 不是"魔数"，就是"把长度补成 53"；
那 10 字节**本来就是要从源存档保留的**（后来改成原地注入后，"保留"变成了隐式的）。

**错误是在 `4b288b4`（"Added AC: Last Raven support"，2022-12-22）里引入的**：
那次为了同时支持 LR，把这段推广成

```cpp
size_t dangling = (isLR) ? 0x15 : 0x35;              // ← 0x35 = 53（真身是"数据长度"）
sum -= (save[prev_check + dangling] + 0x01);
save[prev_check + dangling] = ~(sum + dangling) + 1; // ← 位置从 0x4435 退到了 0x4434
```

顺带一提：那次还把常规段的 `0xFF` 改成了 `0x3FF`，但**这两者模 256 等价**
（`1023 mod 256 = 255`），所以那次改动里**唯一真正的行为变化就是末段校验后退了一个字节**。
又因为上游此后总是**原地注入**（新代码不再显式复制尾部，但原地修改天然保留了它），
两式恒等 ⇒ 这个 off-by-one 一直没有暴露，直到我们从空白块造存档。

## 十一、第二张卡 `Mcd001_final2.ps2` —— 卡死，以及背后我自己的一个 bug

### 结果：**游戏直接卡死**（不是 `破損ファイル`）

第二张卡一次改了两处（NX 的 9 字节作品常量 ×2 + 新增 LR 从零造），

### ★ 自查发现的真 bug：LR 的 4 字节块头

`make_blank_save()` 里的守卫写的是：

```python
if with_header and not is_lr:      # ← LR 分支被整个跳过
```

⇒ **从零造的 LR 块，头 4 字节是 `00 00 00 00`**；而两份真实 LR 存档都是 **`00 44 00 00`**
（u32LE = `0x4400` = 索引 `0x4000` + 调色板 `0x400` = 逻辑载荷长度）。

为什么一直没暴露：**卡 2 是历史上第一次写"从零造的 LR 块"**；此前 LR 只测过
"在真实块上原地注入"，头被原样保留。而 §七 那条"逐字节复原"判据也抓不到它 ——
它只让 `apply_checksums` 作用在真实存档上，**根本没走 `make_blank_save` 这条路**。

⇒ **已修**：新增 `LR_EMBLEM_HEADER = 00 44 00 00` 与 `lr_header_from_save()`；
`make_blank_save()` 现在两种布局都会写块头（`lr_header=` 可覆盖）。
并补上此前缺失的回归断言（`validate_writer.py` §四）：

```
四、★ 从零造：块头里的作品字段必须与真实存档逐字节一致
  （非 LR 比 0x00..0x23；LR 比头 4 字节。对不上 ⇒ 游戏判破損、甚至直接卡死。）
  BASLUS-20644E02_rawblock.raw   头 36 字节一致 ✅      ...
  BISLPS-25462EMB_data0.raw      头  4 字节一致 ✅      真实=00 44 00 00  我们=00 44 00 00
  BISLPS-25462EMB_data1.raw      头  4 字节一致 ✅      真实=00 44 00 00  我们=00 44 00 00
```

`acet_format.py` 自检也加了 `[LR] 空白块头 = 00 44 00 00 : OK` 这一条。

★ **教训（本目录的第三层）**：上一条教训是"对照实验前先确认写入器能逐字节复原已知正确输入"；
这一次说明那句还不够 —— **"复原"只覆盖了读写路径里被走到的那一半**。
空白块创建（`make_blank_save`）、块头字段、以及"从零造"的整条路径，
必须**单独**拿真实存档做一次逐字节比对，否则同样是"全绿却带病"。

而 **`0xDF`（槽位号）正是这一段的第 31 字节**，于是刚设好的槽位号被抹回 0
⇒ 回读时五个槽全是 `0xDF=0` ⇒ **NX 又会卡死**。
正确顺序：写长度 → 清零并写标题 → **最后**写 `0xDF`，并断言。
已把这条写进 `docs/01-项目理解/04-记忆卡与存档处理.md`。

⇒ **教训（第五层）**：**同一张卡上"写徽章数据"和"写元数据"必须当成同一笔事务** ——
元数据的字段会互相重叠（`0xDF` 藏在标题里），写入顺序错了就会静默把前一步的结果抹掉；
而且回读校验必须**逐字段断言**（我这次是因为回读了标题、没回读 `0xDF` 才差点漏掉）。

### 卡 2 的原设计（供对照）

第一张卡 7/7 通过后，剩下两个悬案本想由 `write_final2_test.py`（已清理）**一次问清**
（源卡只读；全盘差异 183 页、**预期之外多改的页 = 无**）：

| 游戏 | 格 | 内容 | 想问什么 |
|---|---|---|---|
| NX | E00 | 紧凑玫瑰 + 作品常量 **清零** | 那 9 字节**是否被校验** |
| NX | E01 | 紧凑玫瑰 + 作品常量 **换成 SL 的** | 是否必须**匹配本作品** |
| NX | E02 | 紧凑玫瑰 + 真常量 | 对照 |

| LR | `data0`/`data1` | **不动**（真实恶魔 / 红树） | 对照 |
| LR | `data2` | **从零造的玫瑰**（块头是 0 —— 就是这个 bug） | LR 从零造能不能过 |

原设计判读（**结果见本节开头：卡死**）：


★ 顺带一个漂亮的旁证（与上面的 bug 无关，仍然成立）：LR 从零造的玫瑰，
