## 三、双向逐像素验证（全部通过）

| 比对 | 字节数 | 不同 | 结果 |
|---|---|---|---|
| 本实现提取 vs **官方 `acet.exe`** 提取 | 65,536 | **0** | ✅ 完全一致 |

| 本实现写回自制图 → 官方 exe 读回 | 65,536 | **0** | ✅ 一致 |

第三条用的是一个刻意刁难自制的输入（见下），它同时验证了**图片处理管线**与**存档写入**：

```
输入：300×300、49,444 色、含 27,919 个半透明像素的合成图
  → tools/prepare_image.py 加工
     ① alpha 二值化(阈值 128)：27,919 个半透明像素归一
     ② 缩放 300×300 → 128×128 (LANCZOS)，alpha 重新二值化
     ③ 减色：11,087 色 → 255 色（中位切分，仅对不透明像素）
     ④ 最终：15,252 个不透明像素用 255 种颜色
  → **官方 acet.exe** 注入真实存档 → 校验 18/18 通过 → 读回逐像素一致 ✅
```

★ 这一步同时证明了"255 色"这个上限是安全的（调色板占 256 项 = 255 色 + 透明）；
如果按上游那个差一 bug 走到 257 项，就会出现透明洞（见
`../docs/01-项目理解/07-限制与已知问题.md` 问题 2）。

### ★ 这份样本还纠正了一个格式误解（★ 后续又被实机再纠正一次）

本目录曾把透明度判据写成"看调色板项的 alpha 字节"。**实机证明游戏看的是索引 0**
（详见 `03-写入实验_data2.md` §一 与 `../docs/01-项目理解/02-存档格式规范.md` §五）。

真实数据（两份 LR 样本的差别**只有一个字节**）：

| 样本 | `palette[0]` | 索引 0 像素 | `--alpha acet`（上游） | **`--alpha index0`（= 游戏）** | `--alpha gs` |
|---|---|---|---|---|---|
| `data1`（红树） | `00 00 00 00` | 732 px | 透明 | 透明 | 透明 |
| `data0`（恶魔脸） | **`00 00 00 40`** | **3,976 px** | 不透明黑 | **透明** ✅ | 50% 黑 |

```
游戏规则（实机定案）：调色板**索引 0 = 背景/透明色**，它的 RGB/alpha 都不当颜色画
                      其余索引一律不透明
                      ⇒ 要"游戏里正确"，背景放索引 0、其余色 alpha = 0x80
alpha 字节的作用        ：[未观测] —— 256 项里只有索引 0 不是 0x80（0x40 或 0x00），
                          而它对显示没有可观测影响
```

★ 本目录已据此给提取加了 `--alpha index0` 档位，并把统计口径改成按索引判定。

### ★ 顺便发现的第二个真问题：`data0` 恰好 256 色，往返会被截断

```
data0：acet 模式提取后不透明色数 = 256 ⇒ 注入需要 257 个调色板项
       ⇒ 上游判据 `size() > 256` 放行 ⇒ 第 257 项索引 256 被截断成 0
实测：官方 exe 走一遍"提取 → 原样注入"，5 个像素颜色被改坏
data1：127 色 ⇒ 128 项，不会溢出 ⇒ 往返 0 个像素变化
```

⇒ **"能提取"不等于"能原样写回"。** 详见
`../docs/01-项目理解/07-限制与已知问题.md` 问题 20 与 21。

## 七、这次验证**没有**覆盖的

诚实列出边界 —— 别把结论用过头：

| 未覆盖 | 影响 |
|---|---|
| **AC3 的 `E##`** | ⚠ 你卡上只有 `S00`（出击存档），**没有 `E##`**。AC3 的 E 族样本仍缺 —— 而 AC3 自己的 ELF 说 E 族长度是 `0x4420`，与"非 LR 应为 `0x4440`"**表面矛盾**，需要真实文件定案（很可能只是"ELF 只读写 `0x4420` 的载荷部分"） |
| AC2 / AC2AA / NX / NB 的 `E##` | 按"非 LR"同一布局处理，未独立验证（卡上有 AC2/AC2AA/NX/NB 的 **`S00`**，但没有它们的 `E##`） |
| 真实 `.psu` / `.max` / `.xpo` | 容器路径只验过 `.PSV`（apollo）与**合成**容器（前缀全 0） |
| 回写容器外壳 | 只做了**读取** `.PSV`；改过的 `.PSV` 能否被 apollo/PCSX2 接受，未验 |
| 回写记忆卡 | ★ **本轮对记忆卡只做了读取**（按工作区规则，写卡必须走"副本 + 用户确认"，且 PCSX2 由用户自己开关） |
| 实机加载 | 按工作区规则 PCSX2 由用户自己跑 —— 注入后的存档能否被游戏正确显示、**左右方向是否镜像**，需要实机确认 |
| PS1 记忆卡 | 完全没有样本；且两个开源来源**结论互相矛盾**（见 `../docs/01-项目理解/04-记忆卡与存档处理.md` §八） |
| 头部 `0x0C..0x23` 的含义 | 已观测（非 LR 样本 ①），但只有 1 个样本，推不出含义；LR 样本 ② 的头部是另一套（4 字节长度 + 12 个 0），也未见非零字段 |
| 255/256/257 色的边界行为 | 只做了代码分析 + 255 色的正向验证 |
